# D0 保真审计 —— 「今天到底丢了什么」

> **状态口径：审计报告（事实陈述）**。本文只陈述**当前代码的客观状态**与**缺口**，
> 不含任何已交付声明。缺口对应的修复批次见 `docs/01-architecture/memory-knowledge-depth-system-spec.md` §8。
>
> **为什么要审计**：设计稿原则 P1（数据保真优先）说「原始证据要保真到够未来算法用」。
> 但「够未来算法用」不能靠口号——必须先知道**今天实际存了什么、缺了什么**。
> 否则一百年后的人打开数据才发现「当时觉得没用的字段没存」，**不可逆**。

---

## 1. 审计对象：D0 的七项保真要求

设计稿 §3 的 D0（原始证据）层承诺保存七类信息：

| # | 要求 | 为什么未来算法需要它 |
|---|---|---|
| ① | **原文** | 摘要/向量都是派生物；原文是唯一不可再生的 |
| ② | **结构**（标题/段落/说话人） | 未来做「按节选」「按说话人归因」时需要 |
| ③ | **双时间**（发生时间 / 记录时间） | 「当时说的」与「后来记下的」可能不同；问「我什么时候说过」要的是前者 |
| ④ | **出处**（哪来的） | 置信度与信任判断的基础 |
| ⑤ | **关系**（与谁相关） | 未来做图算法/联想的前提 |
| ⑥ | **上下文**（在什么场景下说的） | 同一句话脱离场景就变味 |
| ⑦ | **访问史**（谁在何时查过它、为什么） | 最原始的 relevance 标注，是未来算法最珍贵的训练信号 |

## 2. 逐项核实（2026-10-25，实测代码）

| # | 要求 | 现状 | 落点 | 判定 |

| ⑤ | 关系 | **有落点**：知识图谱 `kg_links`、联想 `association_edges` / `association_nodes` / `association_observations` | `crates/engine/memory/src/experience_store_sqlite.rs:59,68,73,81` | ⚠️ **有表，但非 episode 级**（见缺口 G3） |

| ⑦ | 访问史 | ✅ **逐次明细表** `memory_access_events`（含 `query` / `access_kind` / `rank` / `score` / `metadata_json`）+ 聚合表 `memory_access_aggregates`；**且有禁删触发器**（`BEFORE DELETE ⇒ ABORT`） | `crates/engine/memory/src/access_history.rs:128,146` | ✅ **有（且很完整）** |

**结论**：七项里 **3 项齐备（①③④⑦）、2 项半有（②⑥）、1 项有表但不通用（⑤）**。
**最重要的一项（⑦ 访问史）意外地完整**（逐次 + 禁删）—— 这是本次审计最有价值的发现：
「未来算法的金矿」其实**已经在存了**，只是没有人把它当成金矿用。

## 3. 缺口清单（按「不可逆程度」排序）

| # | 缺口 | 后果 | 修复批次 |
|---|---|---|---|
| **G1** | **访问事件没进 D0 的「记录本体」** —— 访问史在**独立的表**里，与 `Episode` 无外键级联、无「这条记录被查过」的**同一事务**保证 | 删记录时访问史可能残留（孤儿访问事件）⇒ 「保真可达率」无法证明 | B1 |
| **G2** | **访问事件没有「谁查的」** —— 有 `subject_id` / `session_id`，但**没有查询主体身份**（是主人本人、是某个 agent、还是后台任务） | 未来做「按人的记忆偏好排序」时缺一维 | B1 |
| **G3** | **关系边不通用** —— 关系存在**知识图谱/联想**那套表里，**episode 之间没有通用边表** | 未来算法想画「记忆网络」时，得跨三套表拼 | B2（`MemoryAnnotation` 落到独立标注区后即可） |
| **G4** | **上下文只有 session_id** —— 场景（在哪、在做什么、什么情绪）没落点 | 脱离场景的记忆无法解释 | B2（D4 标注区可承载，但**原始场景要靠显式写入**） |
| **G5** | **结构无统一落点** —— 段落/标题/说话人分散在各表 | 未来做「按节选」需要跨表拼 | B2 |
| **G6** | **哈希链缺失** —— `append_only` 只有「只追加」，**没有 `prev_hash`/`hash`** ⇒ 无法证明「哪一条被改过」，也无法证明「这一批是完整的」 | 静默篡改/损坏不可检出 | **B1-c**（已派 W-3 下沉链原语） |
| **G7** | **没有 `memory verify`** —— 无「体检」命令：查链、查孤儿、查索引一致性 | 损坏只能等用户发现 | **B1-c** |

> ⚠️ **G1 是本清单里最容易被忽略、也最危险的一条**：它现在**不**造成数据丢失，
> 但一旦有「删除/归档」功能（设计稿 §4 第一/二级），**孤儿访问事件**会让
> 「被删/被归档的记忆是否还能被完整解释」这个问题**答不上来** ⇒
> ⇒ **必须在做删除/归档之前补上**（顺序：G1 → 再做 §4 的归档与销毁）。

## 4b. 内部卷的**真实语料在哪**（2026-10-26 实测）

设计稿 §7.1 的内部卷需要「像人话的问题 + 该命中哪些记录」。**实测本机的真实语料**：

| 候选语料 | 实测结果 | 判定 |
|---|---|---|
| `<数据根>/diary/*.json`（日记） | **只有 1 条**，且是 `dream` 写的认知梦境日志（**非用户内容**）⇒ 挖不出可用题 | ❌ **不可用**（量不够、也不是真实对话） |
| 本仓**文档**（决策简报 / 台账 / 审计报告） | 有内容（如决策简报 384 行、台账 1396 行），但它们是**结构化结论**，挖出来的题会像「文档检索」不像「回忆」 | ⚠️ 辅助 |
| ⭐ **git 提交历史**（`git log --format="%H%x09%s%x09%b"`） | **3531 条提交**；近 300 条里 **18 条**主题含「因为/原因/裁定/决定/理由」等决策词；样本读起来**就是**「当时为什么这么定」 | ✅ **主语料源** |

⇒ **内部卷的真实语料 = git 提交历史**（提交主题 + 正文 body）。
理由：**提交信息本身就是「做了什么 + 为什么」的长期工程记忆**，而且它
① 天然带时间线（可挖 temporal / conflict 型题）、② 带同主题的多次提交（可挖
「后来怎么改的」）、③ 内容天然中文且带决策词（可挖 decision 型题）。

⚠️ **口径提醒**：提交历史是**「工程决策记忆」**，不等于「用户对话记忆」⇒
内部卷测的是「**长期工程记忆的检索与注入**」，**不测**「个人生活记忆」
⇒ 报告里必须写清这个边界（否则会拿它冒充通用能力）。
