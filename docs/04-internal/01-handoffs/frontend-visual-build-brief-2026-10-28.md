## §1 项目一句话

**Apeireth 是一个 AI 工作系统（操作系统式产品）。旧前端被 owner 判定「整体不行」，现在要推倒重建全部视觉方案。**

本阶段的施工目标不是"先接后端跑起来"，而是：

1. **把新视觉语言做出来**（一套可复用的设计系统）；
2. **用高保真、可交互的原型证明它**（三屏 × 明暗双主题）；
3. **让 owner 第一眼说"行"**，并让后续引擎实现有据可依。

> 交付物是**设计原型与规范**：真数据/后端/引擎实现是后续另一条线的事。请不要接后端、不要动生产仓库。

## §2 已定决策（不要重新发明，但可以在其之上做得更好）

| # | 决策 | 含义 |
|---|---|---|
| 1 | **不再以「他」为中心** | 产品不再预设一个中央 AI 人格；界面不围绕"一个伙伴"做情感中心 |
| 2 | **系统状态是中枢** | 首页第一现场是"系统正在发生什么"，不是聊天窗口 |
| 3 | **Agent 是单位** | 用户自带 agent（BYO）；界面把 agent 当作系统里的"单位"呈现 |
| 4 | **「特别关注」双模式** | ① 视觉高亮（pin 一个 agent，界面跟随）；② **指挥授权**（被关注 agent 成为团队 leader） |
| 5 | **能力可授予** | 旧的关系/情绪/记忆/在场类能力 → 变成 per-agent 的能力开关，可随时赋予/剥夺（在 agent 设置面里） |
| 6 | **明暗全双模式** | 所有界面都支持明暗两套；两套各自完整、独立成立（不是暗色反相） |
| 7 | **金色 = 系统信号/能量** | 金色不再专属"他"；只用于系统活动/信号/能量/告警语义，不做装饰 |
| 8 | **三副面孔按工作阶段分** | 指挥仪表盘（中枢/实时）· 技术图纸（工作/配置）· 编辑终端（阅读/详情）；共享一套语法 |
| 9 | **游戏化只到视觉层** | 要"游戏界面般的信息密度与动态感"，不要等级/成就/任务系统等游戏机制 |
| 10 | **业务界面先行，3D 另立项** | 本阶段做的是业务界面；3D 形象/场景/桌宠等不在本次范围 |

## §3 试金石（owner 会拿这句验收）

> **任意一屏，3 秒内回答三问**：系统在做什么？我能做什么？下一步点哪里？
>
> **看一眼就像在操作一台强大的机器**——而不是在浏览一个网页。

## §4 视觉方向（给感觉，不给死规格）

**像什么**：操作系统 / 驾驶舱 / 指挥室 / 游戏界面 / 黑客的电脑屏幕；现代 SaaS 的清晰纪律 + 科幻、高科技、高信息密度、动态、3D 立体感、高级感。

**三副面孔**（同一套语法，不是三套设计）：

| 面孔 | 用在哪 | 默认模式 | 语言要点 |
|---|---|---|---|
| **指挥仪表盘** | 中枢 / 实时值班 / 监控 | 暗 | 发丝网格面板、等宽遥测微标签、中央空间面（agent 编队/系统图）、右侧检查器、时间轴 + 事件日志、回放 |
| **技术图纸** | 工作 / 配置 / 数据审视 | 亮 | 纸白/米白底、黑线稿、工程标注、剖面/图层、单点信号色 |
| **编辑终端** | 阅读 / 长文 / 详情 / 复盘 | 亮 | 强排版（大标题 + 等宽元信息 + 细说明）、高对比、留白节奏 |

**明暗两种气质**（不是反相皮肤）：
- **暗 = 值班指挥**：黑/深蓝底、发光量感、实时遥测——适合"正在发生"。
- **亮 = 图纸工作台**：纸白/米白、黑线稿、工程标注——适合"审视/规划/复盘"。

**参考**：owner 会给/给过一组外部参考页（运营指挥中心、任务控制中心、智能体编队、工程仪表盘、爆炸图工作台、3D 空间叙事等）与开源科幻终端控制台。请**研究其语言，不复制素材/品牌/单页构图**。共同语法见 [参考分析](../../design/reference-language-analysis-2026-10-28.md) 摘要：

1. 近单色底 + **唯一饱和信号色**；
2. 微型等宽标签（大写、字距、中英并置、编号分节）；
3. **发丝网格面板，不是卡片堆**（方角/2px 小圆角、分隔线、紧凑内边距）；
4. **中央空间面 + 四周数据面**；
5. **右侧固定检查器 + 聚焦/关注**；
6. **时间维是一等公民**（日志/回放/倍速/里程碑）；
7. **动态全部是诊断性的**（每个动效都能回答"系统现在在干什么"）。

**反范式（明确不要）**：劣质卡网（大圆角卡片堆、无主次、无真实状态）／纯装饰科幻／低密度大留白／"他"中心显影／静态仪表盘／营销落地页。

## §5 要做的界面（核心三屏 × 明暗 = 6 张）

### 屏 1 · 系统中枢（首页）

- 中央：**agent 编队 / 系统图**（空间面：可以是 2.5D/Canvas，也可以做得更 3D——由你判断，见 §9）。
- 四周：系统遥测（agent 状态 / 任务与队列 / 工具与资源 / 治理与告警）。
- 右侧：**检查器**——被关注 agent 的「此刻 / 正在做什么 / 排队 / 利用率 / 状态 / 可用动作」。
- 时间维：事件日志（当前行高亮）、回放入口、状态时间轴。
- 交互：点击/pin 一个 agent → 检查器切换 + 高亮；明暗切换；至少一个"指挥授权"入口（leader 切换的视觉表达）。

### 屏 2 · Agent 编队 + 特别关注

- 编队视图：agent 分组/站位/连线/状态；每个 agent 有身份、职责、当前状态。
- **特别关注**：pin（视觉高亮）与**指挥授权**（leader）两种模式的视觉差异必须可辨认。
- 检查器 + 动作（打断/重派/下线等——语义按本产品，动作名可自拟）。
- 要能看出"谁在干活、谁在排队、瓶颈在哪"。

### 屏 3 · 会话 / 工作流视图

- 即时通讯的熟悉模型（会话列表 / 消息流 / 通知 / 群组 / 红点）——降低学习成本。
- 工具过程、审批卡、任务状态等作为系统事件的延伸出现。
- 与中枢的关系：会话是中枢的一种视图，不是全部。

### 每屏必须包含的状态

默认 / 选中 / 告警 / 空态 / 加载 / 错误 / 权限不足（至少覆盖前 5 种）；有 mock 数据必须显式标注。

## §6 交付物清单（D1–D7）

> **D1/D2/D3 的关系（先读）**：三件都是 HTML/CSS/JS 产物，区别只在粒度与用途——
> **D1 = 设计标准（配方，不是草稿；后面所有零件与页面都从它派生）**；
> **D3 = 零件图纸 + 状态样件（把整页拆成单个组件，每个组件给全部状态）**；
> **D2 = 成品（把零件组装成三屏整页）**。逻辑顺序 **D1 → D3 → D2**。

| # | 交付物 | 要求 |
|---|---|---|
| **D1** | **设计标准 v0.1** | 令牌（颜色/字阶/间距/圆角/层级/动效/材质）明暗两套；网格；图标规则；一页可读规范 + 可复制的 token 清单。**不是草稿**：D2/D3 必须从它派生 |
| **D2** | **三屏 × 明暗 = 6 张成品** | 基准 1440×900，至少考虑 1280 / 1920 自适应；每屏可截图当作品；覆盖默认/选中/告警/空/加载等主要状态 |
| **D3** | **组件与状态矩阵（零件图纸）** | 把整页拆成零件，每个给**全部状态**的 HTML/CSS 样件：输入框（空白/聚焦/已填/禁用/错误/IME）、按钮（默认/悬停/按下/loading/禁用/危险）、列表行（默认/选中/悬停/空/加载/错误）、检查器/卡片（正常/告警/权限不足）、时间轴/日志（实时/历史/回放）、弹层（打开/关闭/危险确认）、mock 标注、空/错/载三态 |
| **D4** | **可交互原型** | 可直接运行（HTML/CSS/JS 单页或目录均可，尽量无构建步骤、依赖尽量少）；pin/切换 agent/明暗切换可操作 |
| **D5** | **设计说明** | 设计决策、与参考的取舍、0 装标注方式、实现注意事项（哪些效果依赖 Canvas/WebGL、降级方案） |
| **D6** | （鼓励，可选）**中央屏的大胆变体 1 个** | 展示你对"3D 立体感/游戏级反馈"上限的理解——**不要被现有实现条件限制** |
| **D7** | **素材与许可声明** | 字体/图标/图片/3D 素材来源与许可；不得使用来源不明素材 |

## §7 硬约束（是底线，不是能力上限）

1. **无预设"他"**：界面里不能出现"系统自带的中央 AI/人格"；agent 是用户带入的单位。
2. **明暗两套都精细**：每屏两种模式都要独立成立；"暗色精细、浅色糊弄"直接不算完成。
3. **0 装**：原型可用固定数据，但必须显式标注 mock；动效必须有状态来源（不能为动而动）；空态写数据契约（"当 X 发生时这里会出现 Y"）。
4. **不做游戏机制**（等级/成就/积分），只做视觉层的密度与动态。
5. **不做营销落地页 / 单页概念站**：这是产品界面，不是作品集主页。
6. **可读性优先于炫技**：高密度但不拥挤；层次清楚、扫读顺畅。
7. **无障碍基线**：明暗对比度、键盘可达、`prefers-reduced-motion`。
8. **版权**：参考页只取语言；不复制素材、Logo、品牌字体；自产或使用可商用素材并署名。
9. **性能**：交互流畅（目标 60fps）；重效果要有降级；首屏可交互时间合理。
10. **范围**：不接后端、不接生产仓库；交付物交给 owner，由我们后续与引擎线对接。

## §8 验收（owner + 总工程师）

- [ ] **owner 审美**：对三屏（明暗双份）显式说「行」——这是唯一主观门，不可替代；
- [ ] **D1 设计标准完整**，且 D3/D2 确实从它派生（不是三套各写各的）；
- [ ] **D3 组件状态矩阵**覆盖：输入框/按钮/列表行/检查器/时间轴/弹层/空/错/载/权限/mock 标注；
- [ ] 三屏 × 明暗完整、可交互、状态齐全（默认/选中/告警/空/载/错/权限）；
- [ ] 设计系统可作为引擎实现源（令牌可导出、组件语言清晰、无"只可远观"的模糊规范）；
- [ ] 设计说明完整：取舍、降级方案、mock 标注方式；
- [ ] 无违规素材；无可识别的"预设他"；
- [ ] 反范式逐条不出现（见 §4 末）。

## §9 自由条款（要求施工方读三遍）

> **以上全部是方向与底线，不是能力上限。**
>
> - 在不违反 §7 硬约束的前提下，**请大胆给出你认为更好的设计决定**（版式、材质、动效、3D 语言、交互方式），并在设计说明里解释"为什么更好"。
> - 如果某条约束与你的设计判断冲突，优先保证三条：**系统可读、状态可追、明暗对等**；其余可以提出替代方案。
> - **不要为了"稳"做成普通 SaaS**（那就没有存在意义）；**也不要为了"炫"牺牲可读性**（那就不可用）。
> - 中央空间面（agent 编队）是这套设计的"脸"：可以用 HTML/CSS 2.5D、Canvas、WebGL 或混合方案——**按你认为最好的效果做**；只需在设计说明里写清依赖与降级。
> - 如果一次交付做不完，**首轮优先 D1 设计标准 → D2 三屏成品（明暗双份）→ D3 组件状态矩阵**（D3 若首轮做不完可放第二轮）；D4/D5/D6/D7 放第二轮打磨。
