### 1.2 为什么判定「整体不行」（owner 已确认的 5 条诊断）

1. **氛围很强、产品很弱**：背景（黑洞/星云）承担几乎全部身份，前景组件是通用暗色面板——弱排版、低对比、无材质；错误态裸奔（如「拉取活动记录失败 / Failed to fetch」原样上屏）。**组件层没有真正的状态设计**。
2. **天平压反了**：`01-DESIGN-SYSTEM.md` §1「电影感优先于信息密度」直接产出——该密的地方（工作台/治理/设置）大留白，该静的地方（聊天）没有真正的显影层次；结果既不像工具，也不像电影。
3. **信息架构是聊天壳单中心**：能力藏在 Ctrl+K 与 5,314 行设置页深处，没有「指挥面」；62 组件的组织方式随功能线性膨胀。
4. **技术基底不可测**：渲染层与测试层被编译边界割裂（38 条源码镜像测试钉字面量），任何视觉重构都会被旧测试撕碎。
5. **视觉语言单一调**：深空+金+黑洞是唯一母题，缺一套自己的排版/网格/材质/图标系统；换主题只是换皮。

**证据落点**：`previews/backend-chat-real.png`、`previews/mode-engineering.png`（现状截图）；代码规模见 §1.1。

### 1.3 旧线里哪些东西**留下**（不是白干）

| 资产 | 处置 | 理由 |
|---|---|---|
| `ui-core`（响应式/依赖图/调度）、`ui-dom`（差分/事件/绑定）、`ui-macro`、`ui-gpu`（双后端 GPU 桥） | **留作地基**（继续维护/补齐） | 与「旧设计」无关的能力层，新线直接复用 |
| `apeireth-ui-demo/harness/` 证据装置（抽取器/浏览器驱动/像素 & DOM & 帧对照） | **留作能力工具** | 新线用同一套装置验证「原型 vs 引擎」与「引擎 vs 设计稿」，目标从「对照旧设计」改为「对照新设计稿」 |
| `ui-kit` 里的旧设计组件（`tool_card` / `tool_grid` / `status_bar` / `governance_tab` / `settings_*`） | **冻结为参考件（FROZEN）** | 可读不可改；新组件按新设计重建，不复用旧外观 |
| 已完成面的像素证据 | **冻结入库** | 证明「引擎能逐像素复刻一套复杂设计」的能力，不证明新设计 |
| 设置页剩余 5 子面（预算/数据/人格记忆/能力治理/服务商） | **停止迁移** | 旧设计将被替换；它们目前只是显式未接线桩，无沉没成本 |

## §2 目标形态

### 2.1 终局定义

```
新视觉语言（范式驱动）
      │
      ├─ 设计系统 v1（令牌/网格/排版/密度/材质/动效/图标族/无障碍）
      │
      ├─ 新信息架构（入口/导航/视图/卷宗/命令面）
      │
      └─ 新前端实现（自研引擎 wasm → Tauri WebView 宿主，宿主不改）
                │
                └─ W4 生产切换（旧 Svelte 退役）

华服线（W5，另计划）：3D 形象 / 场景 / 桌宠 / 图标族 / 启动动画
```

- **基底**：自研引擎（`crates-ui`）为最终实现载体；Svelte 仅作 W1 设计原型载体。
- **宿主**：Tauri `src-tauri/`（13,476 行 / 45 commands）**复用不改**。
- **数据面**：后端契约不动；新前端按后端契约重新核对/接线（`runtime.ts` 仅作参考，不作依赖）。
- **多形态**：TUI/多客户端**不在本计划范围**，未决。

### 2.2 成功判据（四层，缺一不成立）

| 层 | 判据 | 谁判 |
|---|---|---|
| **L-A 审美** | owner 对每面/每波**显式**说「行」——并排看、可截图、可复跑；主观门**不可代签**，不通过须书面理由 | owner（艺术总监） |

### 2.3 不做什么（Non-goals）

- **不**改后端、不改 Tauri 宿主、不改主 workspace、不改 LOCKED。

- **不**在业务界面稳定前开华服线（3D/场景/桌宠/图标族/启动动画）——顺序由 owner 定，不抢跑。
- **不**为赶进度放宽任何一层门（见 §6）。

## §3 作战原则（bold ≠ 失控）

1. **设计先行，实现后追**：先让设计在便宜载体上试错，再在目标载体上实现；禁止「先造框架再想设计」。
2. **每批可回滚**：W0–W3 生产前端 0 改动；W4 走开关/双入口。
3. **单一真源**：设计令牌/组件规范/证据装置各一份；原型与引擎从它生成或对照。
4. **眼判与机判分离**：审美门只能 owner 判（不可代签）；行为/数据/工程门必须机械可判。
5. **0 装**：无真实来源的动效/数据不上屏；模拟态显式标注；未接线写「未接线」。
6. **半成品不弃尸**：任何中道停机必须留「已完成/未完清单」（宪章 §二.3）。
7. **范围锁**：业务界面完成并切换前，华服线不开工；TUI/多形态不夹带。

### 4.2 W1 · 打样（设计 × 基底双验证）

**目标**：用 3 屏回答两个问题——「这套设计行不行」（owner 审美）与「引擎作为最终载体行不行」（数据裁定）；产出基底裁定建议。

**打样屏（3 屏，覆盖三种界面制度）**：

| # | 屏 | 覆盖的界面制度 | 必含交互 |
|---|---|---|---|
| 1 | **会话主屏** | 流式/时间性/情感层 | 发送、流式追加、工具过程展开、审批卡浮起、空态 |
| 2 | **工作台/指挥面** | 高密度/多视图/读数 | 多面板、列表/表格、状态条、筛选、快捷动作 |
| 3 | **设置或卷宗** | 表单/长页/治理 | 分区导航、表单控件、危险操作确认、错误/空态 |

**双载体**：

- **Svelte 原型**（设计载体，快）：可直接用现有前端栈，喂固定数据（标注 fixture），优先把「设计意图」跑起来；
- **引擎实现**（目标载体）：同一设计、同一数据，在 `crates-ui` 上实现，产物可跑（wasm）。
- 两侧并排对照：**不是**与旧 Svelte 对照，而是**原型 vs 引擎**对照（验证引擎能否还原创作者意图）。

**量测表（W1 必报，全部实测）**：

| 维度 | 指标 | 采集方式 |
|---|---|---|
| 设计还原 | owner 主观评分（每屏 1–5 或通过/不通过）+ 原型 vs 引擎的截图/结构证据 | owner 评审记录 + 像素/结构差异证据（复用现有 harness） |
| 工程墙钟 | 每屏实现墙钟（AI 施工线，分钟）+ 产出（Rust 行/测试数） | 施工日志 + `git show --numstat` 口径 |
| 性能 | 首屏/帧率/内存/包体（Chromium 与 Tauri WebView 两处；测不到的写「未实测」） | 探针脚本（W1 落地） |
| 可测性 | 行为测试数 / 覆盖的交互路径 / 是否有源码镜像 | 测试清单机械计数 |
| 可维护性 | 组件行数分布 / 依赖边增量 / 设计令牌覆盖率 | 机械统计 |

**基底裁定门（owner 主持）**：拿 W1 数据回答「引擎能否达到设计/工程门」——通过 ⇒ 引擎继续作最终载体；不通过 ⇒ owner 用数据裁定调整（例如扩大 Svelte 原型的角色，或调整引擎边界），**本计划不预设结论**。

**W1 退出条件**：3 屏双载体可跑 + owner 审美门（通过或明确修改方向）+ 基底裁定记录落档。

### 4.3 W2 · 立骨（设计系统 v1 + 新 IA + 新壳 + 引擎缺口）

**目标**：把 W1 选定的方向固化成**可量产的设计系统**与**新骨架**，并把引擎缺口补齐到能承载 W3 铺面。

**交付物**：

1. **设计系统 v1（冻结）**：令牌（颜色/字阶/间距/圆角/层级/动效/材质）、网格与布局制度、密度模式、图标族规则、无障碍基线（对比度/焦点/动效减弱）、组件清单与状态矩阵。
2. **新信息架构（IA）**：入口/导航/命令面/多视图/卷宗/通知位置；每个「面」的边界与数据契约。
3. **新壳**：应用外壳（启动/首启/主布局/导航/命令面/通知）；在引擎上跑通。
4. **引擎缺口补齐**（清单来自 W1 + 引擎审计，候选：真实 Tauri WebView 验证、输入/IME、滚动/虚拟列表、布局测量、富文本/Markdown、焦点/键盘/无障碍、资源管线（图标/图片/字体）、错误边界、主题/密度切换、dev 体验）。**每项缺口 = 可验证的关闭证据**。
5. **证据装置升级**：对照目标从「旧设计」改为「设计稿/原型」；生成物 `--check` 可复核。

**硬门**：
- 设计系统 v1 由 owner 签署冻结（之后变更走版本化）；
- 新壳在**真实 Tauri WebView** 内跑通一次（旧线遗留的最高风险项）；
- 引擎缺口清单关闭率与剩余项诚实登记（未关闭项不得藏着进 W3）。

### 4.4 W3 · 铺面（业务界面逐面重建）

**目标**：把业务界面按波次全部重建在引擎上，每面过「双层门」（§6），业务界面完成即进入 W4。

**波次（建议序；每波内可并行面，波与波有数据/壳依赖）**：

| 波 | 面 | 交付 | 依赖 |
|---|---|---|---|
| **波 1** | **会话主屏**：消息流 / 流式 / 输入 / 工具过程 / 审批卡 / 空错态 | 打通「一条真流」端到端（真后端数据） | W2 新壳 + 数据接线 |
| **波 2** | **工作台/指挥面**：多视图 / 状态条 / 通知 / 诊断 / 快捷入口 | 高密度面成立（owner 最能感知「强不强」的一面） | 波 1 的组件与数据通路 |
| **波 3** | **工具面 + 治理卷宗**：工具卡 / 工具网格 / 审批 / 审计 / 守卫 / 授权 | 治理面全量重建（旧线已有完整对照件可作参考） | 波 1 审批卡 |
| **波 4** | **设置页**：框架 / 外观 / 模型 / 人格 / 能力 / 预算 / 数据 / 服务商 / 向导 | 5,314 行旧页面的替代 | 波 2/3 的控件与数据 |
| **波 5** | **系统面**：启动动画 / 首启 / 桌宠入口 / 错误恢复 | 业务界面收口 | 波 1–4 |

**每面完成判据（六条，缺一不算完）**：

1. owner 审美门：显式通过（并排看真跑产物，不接受「看着差不多」）；
2. 行为测试：真调用生产模块（禁源码镜像），钉交互路径/分支/回调；
3. 数据真接：真后端（REST/SSE）或显式 fixture 标注（fixture 不得伪装成真数据）；
4. 空态/错误态/加载态：三态都有设计，错误态不裸奔；
5. 0 装：无源动效不上屏；模拟态显式标注；
6. 证据入库：截图/帧/量测 + 复跑命令随批落盘。

**测试债规则（本线硬纪律）**：
- 新线**禁止**源码镜像测试（不读源码文本断言）；
- 旧 38 条源码镜像测试**不迁移、不复制**——它们随旧前端一起在 W4 退役；
- 旧前端在 W4 前继续跑生产 ⇒ 旧测试保留以保护生产，但其覆盖不算新线的验收。

### 4.5 W4 · 换芯（生产切换 + 旧前端退役）

**目标**：把生产 Tauri 应用切到新前端，旧 Svelte 退役，且**可回滚**。

**交付物 / 门**：
1. 生产打包切换方案（开关/双入口/回滚形态）——切换前设计、写入交付卷宗；
2. 生产包实测（启动/核心流/数据/错误恢复）；
3. owner 主观验收（真机、日常场景，非只看截图）；
4. 回滚验证（关开关回旧包，一条命令级步骤）；
5. 旧前端冻结/归档（不删除历史，标记退役）。

**不在本阶段**：华服线（W5）、TUI/多形态。

### 4.6 W5 · 华服（另计划，不在本计划承诺）

3D 形象 / 场景 / 桌宠 / 图标族 / 启动动画。owner 已定范围与顺序（业务界面之后），但**阶段计划、引擎路线（3D 栈）与验收门另出计划**——本计划只保证：业务界面完成后立即具备开工条件（素材/资产盘点在 W0–W2 随行完成）。

**新产品前端的落点**：W2 决策（在 `crates-ui` 内新建 app crate 或演进 `apeireth-ui-demo`）。若新增 crate ⇒ 按契约规则另出 ADR 并更新 `contract.toml` §[vendored].ui_engine 清单（当前 7 crate）。

### 5.2 并行与写域纪律

1. **1 批 = 1 个 write_scope = 1 个 commit**；开工前声明三段（主战场 / 随行 / 禁区零触碰）。
2. **串行依赖**：W0 → W1 → W2 严格串行；W3 内**按面并行**（写域不相交才可并）。
3. **共享文件只由主线改**（`main.rs` / `lib.rs` / 设计令牌生成器 / CI）——各面只填自己的模块文件（旧线已验证该模式可行）。
4. **不碰他线**：`frontend/companion-desktop/`、`crates/**`、根 `Cargo.toml`/`Cargo.lock` 全程禁区。
5. **中道停机**：必须留「已完成 / 未完清单」（宪章 §二.3）。

### 5.3 预算与速率口径

- owner 2026-10-28 定：**不设人日预算**；每批报「AI 施工线墙钟 + 实测产出」。
- 历史参考（**不作为本线承诺**）：旧线 P0–P3 实测 19,988 行 / 117 分钟 ≈ 170.8 行/分钟（插入行数 = 各 commit `git show --numstat` 之和；时间 = commit 时间戳）。本线每批自报实测值，不换算人日。
- P4 成本门（「重估 ≤ 剩余预算」）在无预算给定时的口径：**如实标注「owner 未给预算、成本门不闭合」**，不伪造判定。

### 5.4 owner 评审节奏（提案，owner 可改）

| 时点 | 形式 | 产出 |
|---|---|---|
| W0-D 后 | 方向评审会（60–90 分钟） | 选定方向/杂交配方（书面） |
| W1 后 | 打样评审会 + 基底裁定 | 审美门 + 基底裁定记录 |
| W2 后 | 设计系统冻结评审 | 设计系统 v1 签署 |
| W3 每波末 | 面级验收（可批量看真跑产物） | 每面通过/不通过（书面） |
| W4 | 生产切换验收（真机日常场景） | 切换放行/回滚 |

> 节奏是**提案**：owner 的时间是稀缺资源，宁可批量、不可代签。

## §6 验收体系（双层门）

| 门 | 判据 | 谁判 | 证据落点 |
|---|---|---|---|
| **A 审美门** | owner 对真跑产物显式「通过」；不通过须书面理由；「看着差不多」不算通过 | owner（不可代签） | 评审记录 + 截图/录屏 |
| **B 行为门** | 行为测试真调用生产模块（禁源码镜像）；覆盖交互路径/分支/回调；空/错/载三态齐全 | 机械门 | 测试清单 + 运行日志 |
| **C 数据门** | 真后端数据（或显式 fixture 标注）；未接线写「未接线」 | 机械门 + 接线线 | 接线账/请求日志 |
| **D 一致门** | 设计令牌/组件规范单一真源；原型与引擎同源生成物 `--check` 0 漂移 | 机械门 | 生成物 + `--check` 日志 |
| **E 工程门** | `crates-ui` 四关 + wasm 构建 + `cargo deny` + 主仓 0 改动 + LOCKED 0 触碰 | 机械门 | 门禁日志 |
| **F 0装门** | 无源动效不上屏；模拟态标注；「未实测」不写「已通过」 | 机械门 + 总工程师审查 | 每批 commit 正文 / 交付卷宗 |

**门禁执行**（沿用宪章）：
- `crates-ui`：`cargo check/clippy -D warnings/fmt --check/test` + `cargo build --target wasm32-unknown-unknown --release` + `cargo deny check`；
- 主仓：`git diff --name-only -- frontend/ crates/ Cargo.toml Cargo.lock` = 0（本线）；
- 文档：`docs_links.py --check` / `docs_index.py --check` / `check_doc_caliber.py` / `docs_truth.py --verify --check`。
