# 问责闭环设计 —— 影响声明 / 决策回执 / 后果追踪 / 通知义务

> 日期：2026-10-23 · 状态：**设计（待实施）** · 上位：ADR-0014 §5、ADR-0013 §2.2
> 触发：外部顾问判据 ——「记录 ≠ 负责」、「可纠正若只改视图，那叫数据纠正，不叫责任闭环」

## 1. 问题：我们有"可纠正"，没有"可问责"

现状（已核实）：

- 纠正机制是**技术性**的：append-only 原始行不动、检索走 override、revision CAS、审计链；
- 但**纠正只作用于记忆视图**：用户此前基于旧结论做的决策（买过、签过、发过、投过）无人处理；
- 审计链记的是**系统动作**，不是**用户行动的影响**；
- 自查工具（`audit_unwired.py` / 未接线台账）能证明"能力没接电"，**证明不了"影响被追踪"**。

顾问的一句判据：

> 若系统知道某记忆被纠正、且知道旧结论曾驱动求职/购买/发信，却只改视图然后宣布"已纠正"——**那叫数据纠正，不叫责任闭环**。

## 2. 四个构件（按依赖顺序实施）

### 2.1 影响声明（Impact Statement）—— 行动时写

**何时**：任何**外部行动**（发消息、提交表单、下单、调用外部 API、把上下文送出边界）发生时。

**写什么**（不含内容原文，只含指涉与依据）：

```json
{
  "action_id": "act-…",
  "at_ms": 0,
  "boundary": "provider|third_party|user_to_org|inference_to_action",
  "facts_used": ["ep-…", "ep-…"],          // 用了哪些记忆条目
  "inferences": ["inf-…"],                 // 哪些是推测（与事实分开）
  "grants": ["grant-…"],                   // 哪些权限允许了它
  "affected": ["self"],                    // 影响了谁（self / named-party / unknown）
  "reversible": true,                      // 结果是否可逆
  "destination": "provider:anthropic"      // 目的地（不含内容）
}
```

**代价**：延迟、存储、界面复杂度；**没有它，后续纠正无法定位影响**。

### 2.2 决策回执（Decision Receipt）—— 行动后给用户

**是什么**：面向**被影响的人**的一行话，不是日志。

> 我做了什么、依据什么、发给谁、还能不能撤回。

**与日志的区别**（必须写进实现注释）：

| | 日志 | 回执 |
|---|---|---|
| 面向 | 审计 | 被影响的人 |
| 内容 | 全量结构 | 一句话 + 可展开依据 |
| 渠道 | 文件 | 会话/面板/通知 |

### 2.3 后果追踪（Consequence Tracking）—— 高影响行动后

**何时**：`reversible=false` 或 `affected != self` 的行动。

**要回答**：邮件是否发送？申请是否提交？购买是否完成？

**代价**：连接器复杂度与隐私负担；**没有后果状态，系统无法知道自己是否需要补救**。

**最小实现**：行动回执带 `outcome: pending|confirmed|failed|unknown`，
由回执渠道或用户确认回填；**unknown 必须显式表示**（不假装知道）。

### 2.4 通知义务（Notification Duty）—— 纠正发生时

**何时**：纠正一条旧事实，且该事实曾被至少一次外部行动引用（查 2.1 的影响声明索引）。

**产出**（必须落到用户可见处）：

1. **受影响事项列表**（哪几次行动、何时、去了哪）；
2. **影响程度**（事实被推翻 / 部分修正 / 仅措辞调整）；
3. **建议补救动作**（撤回消息？重发更正？联系对方？）；
4. **是否需要用户授权**（系统不擅自"到处发信"）。

## 3. 责任判据（回答"用户没听/没注意/系统没推"）

顾问给的三因素：

1. 系统是否**知道**风险；
2. 系统是否有**合理机会**提醒；
3. 用户是否能**合理理解**提醒。

**应当负责**：把高影响结论包装成确定事实；知道错误已扩散却保持沉默。
**责任较弱**：低风险建议 + 充分披露 + 用户主动越过提醒。

## 4. 与既有组件的关系（不另造系统）

| 既有 | 复用方式 |
|---|---|
| `governance-audit.jsonl`（哈希链） | 影响声明**追加**到同一链路，不另建账 |
| `RedactionBridge` 零真值账本 | 影响声明同样**零真值**（只指涉 id，不含原文） |
| 记忆治理视图 + revision CAS | 纠正事件作为通知义务的触发源 |
| 自述面 `self_status` | 新增只读子对象：近期影响声明计数 / 待确认回执数 / 未处理通知数 |
| 未接线台账 | 本设计落地前，相关能力如实标 `IMPLEMENTED 未接线` |

## 5. 实施顺序（每步可独立合并、可回滚）

1. **影响声明 + 索引**（写到治理审计链；零真值；默认关）；
2. **决策回执**（会话内一行 + 可展开；不新增通道）；
3. **后果追踪**（`outcome` 字段 + 显式 `unknown`）；
4. **通知义务**（纠正时查索引 → 生成待办，不自动外发）；
5. **自述面接入**（只读计数，沿用 probe 纪律）；
6. **默认开启评估**（有真实数据后再谈）。

## 6. 测试计划

- 影响声明：外部行动必写一行；零真值（grep 断言无原文）；边界枚举闭合；
- 回执：行动后必有回执；撤回后回执更新；
- 后果追踪：`unknown` 显式；不假装 confirmed；
- 通知义务：纠正被引用事实 → 生成待办；未被引用 → 不打扰（负例必测）；
- 默认关：关时逐字节零变化。

## 7. 不做

- 不自动替用户"到处发更正"（通知义务 ≠ 自动外发）；
- 不追踪用户在本系统之外的行动（管不了的，如实说管不了）；
- 不承诺 provider 侧删除（只在承诺范围内保证 + 披露边界）；
- 不为追踪而收集内容原文（只存指涉 id）。
