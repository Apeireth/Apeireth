# W5 决策：哲学拦截层（`ActionGuard`）**不接**回热路径 —— 阻塞不在接线，在动作描述

- **日期**：2026-10-24
- **触发**：owner 授权「W5 按你的建议来就行」
- **结论先行**：**不接**。接上去等于装样子。真正的阻塞不是「缺一根线」，
  而是「**没有可供判定的动作描述**」——而那是产品设计决策，不是接线工作量。

---

## 1. 先摆事实（查证结果，不是推测）

### 1.1 `ActionGuard` 本身是完整的三重门

`crates/foundation/core/src/gate.rs`：V1 哲学守门（13 键）+ V2 权限洋葱（风险等级 → 层）
+ V3 真实人类批准（HA），三者 AND。逻辑本身写得对，且 2026-09-24 审计修过两处
**真实退化**（V2 的 `|| true` 恒真、V3 的 `_ => true` 全放行）。

### 1.2 但它现在的调用点只有测试和示例

全仓引用：`crates/foundation/core/src/lib.rs` 的单元测试 + `examples/hello_world.rs`。
**执行主链零调用。**

### 1.3 致命的一条：`ActionTarget` 里 13 个变体，10 个是测试夹具

```rust
pub enum ActionTarget {
    ModifyL0HA,          // 生产语义：永远被禁
    ReorganizeOnion,     // 生产语义：物理隔离 + 多签
    ModifyEvolutionL0,   // 生产语义：Evolution 不能改 L0
    PretendClone, PretendPerfect, PretendUuid,   // 「PHL-01 故意违反（测试用）」
    PretendUndo, PretendSafe,                     // 「PHL-02b 故意违反」
    PretendSpecIsProof, PretendCounterexampleIsNotBug, // 「PHL-03 故意违反」
    // … 其余同理
    NormalAction(String),
}
```

源码注释自己写着「**12 键 hardcode 测试用**」。也就是说：这个枚举是**为验证哲学键而设计的
测试夹具集合**，不是「运行时要做什么」的描述语言。

### 1.4 后果：真实动作映射不到任何 target

工具调用（`shell` / `file_write` / `fetch` / `memory_write` …）能映射到哪个 target？

- 映射到 `ModifyL0HA` / `ReorganizeOnion` / `ModifyEvolutionL0` —— **语义完全不成立**
  （这些是「改人类权威根 / 重组权限洋葱 / 改进化层 L0」，当前系统里**没有工具能做这些事**）；
- 映射到 `NormalAction(desc)` —— V1 对 `NormalAction` **不触发任何哲学键**
  ⇒ 永远 `Allow` ⇒ **门形同虚设**；
- 映射到 `Pretend*` —— 那是「故意违规」的测试夹具，生产上用等于把正常动作当违规。

**三条路都通向「装样子」。**

### 1.5 V3 依赖的真多签也还是 0 装

`check_ha` 的注释自己写着：「v2.0 0 装：signature 是 hex string，非真 crypto 校验」。
这是台账 **W2**（多签）的状态 —— 明确等 v2.1。

## 2. 我的建议（这也是裁定）

### 2.1 不接热路径

**理由**：我们的一贯口径是「0 装诚实」。把 `ActionGuard` 接到热路径上，会有两种结局：

| 结局 | 实际效果 | 诚实度 |
|---|---|---|
| 塞 `NormalAction` | 永远 Allow，**拦截力为零** | ❌ 但看起来像"有哲学守门"了 |
| 塞 `Pretend*` 式映射 | 误拒正常操作 | ❌ 更坏 |

两者都是「**记录 ≠ 负责**」的同一个错误：装上了不等于管住了。

### 2.2 台账 W5 的状态要改准：阻塞于**产品设计**，不是阻塞于接线

原台账写「触发：哲学拦截层重新上热路径时一并接」—— 这个措辞暗示「只差一次接线」。
**这是错的。** 真实状态是：

> 缺少的不是一根线，是一种语言 —— **「运行时的这个动作，哲学上是什么？」**
> 这个问题的答案决定了风险等级与目标，而它是产品设计（谁描述动作、描述多细、
> 谁来维护映射表），不是工程接线。

### 2.3 重新定义触发条件（可判、可执行）

**不接**，直到下面两条**同时**成立：

1. **出现需要这道门的动作**：系统里出现「能改 L0 人类权威 / 能重组权限洋葱 /
   能改 Evolution 层 L0」的**真实能力**（现在没有 —— 所以这道门现在没有防守对象）；
2. **有了动作描述语言**：存在 `governance::Action → core::Action` 的**经产品确认的**
   语义映射（风险等级 + target 的判定规则），且映射表有人负责维护。

在此之前，`ActionGuard` 保持**库级完整、独立测试、零生产调用** —— 这不是「未接线」的缺陷，
是「**防守对象尚不存在**」的正常状态。

### 2.4 替代方案（如果非要观测）：影子模式，但要先做映射草案

若将来想提前积累数据，正确顺序是：

1. 先写**映射草案**（capability 名 → 风险等级），在文档里评审；
2. 再写影子判定器（跑 AND 门、**只记录不拦截**、默认关）；
3. 用真实数据回答「如果接上去会拦掉什么」；
4. 有数据后才谈「真接」。

**跳过第 1 步直接写影子判定器 = 拿垃圾映射产出垃圾数据**，比不做更坏。
故本批**不写**影子判定器 —— 避免留一段无人维护的死代码。

## 3. 本批实际做了什么

- 本页（决策与依据）；
- 台账 W5 状态改写（把「只差接线」这个误导性措辞改准）；
- **零代码改动**（不接、不写死代码）。

## 4. 一句话

> **接一个没有防守对象的门，不叫安全，叫装饰。**
> W5 现在缺的不是线，是「这个动作在哲学上是什么」的语言 ——
> 而那是产品设计，等你定。
