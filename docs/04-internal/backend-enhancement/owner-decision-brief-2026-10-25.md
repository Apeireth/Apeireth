## D-1｜`dead_code` 全局 allow → 是否改成 warn + 棘轮

**现状（证据）**

`Cargo.toml` `[workspace.lints.rust]` 里 `dead_code = 'allow'`，注释写明原因：

> 9 个 missing_docs + 1 个 unused_imports + **1 个 dead_code** + …
> 都在其他 AI 协作者正在改的 src 文件, 不能直接改源码清, 全部 allow.

即：**当时只有 1 处** dead_code 警告，为了让那一个文件不被卡，把整个 workspace
的这道 lint 关掉了。

**代价（我这轮实测）**：临时打开 lint 拿到 60 条线索，逐条核验后确认 ——

| 线索 | 结论 |
|---|---|
| `five_dimensional.rs` 的 `recent_memories` | **真缺陷**：宣称 5 维记忆，`export` 只产出 4 维（`Recent` 从不产出），已修 |
| `emergence.rs` 的 `initial_depth` | 冗余副本，已删 |
| `streams.rs` `StreamHandle`、`episode.rs` `query_recent` | 真死 API，已删 |
| `plugin/llm_factory.rs` `role`/`model`、`tools/doc_ops.rs` `obj_ref` | **在副总指挥区**，我只报不动 |
| 其余 ~55 条 | 测试夹具 / `_` 前缀保留 / `cfg(kani)` 面（不是死代码） |

**选项**

| 选项 | 影响 |
|---|---|
| **A. 改成 `warn` + 基线棘轮**（只减不增） | 这类「字段/函数存了不用」以后**能被机检挡住**（正是「能力齐全但没接电」最常见的形态）；代价：需先清 60 条（会动到副总指挥区 2 处、CI workflow 属他范围） |
| B. 保持 `allow` | 零风险，但这类缺陷只能靠人搜（我这两轮靠临时打开才找到） |
| C. 改成 `warn` 但只在**新增代码**上生效（`#[deny]` 局部标注） | 折中：老代码不动，新代码受管；但需要作者自觉加标注，机检强度弱 |

**我的建议**：**A**，但**分两步**：先由副总指挥把他在区里的 2 处清掉（或确认可以 allow
带理由），然后一次性开 `warn` + 棘轮。收益远大于成本：这条线是我这轮唯一能系统发现
「字段存了不用」的机检手段。

**不裁定的后果**：继续靠人肉搜索；同类缺陷会持续被埋（我已找到 4 个真实例）。

## D-2｜`council ballot` 未持久化 —— 需要定「一个顾问评价如何折算成一张票」

**现状（证据）**

`apeireth nightwatch` 自报缺口：「council ballot 未持久化 —— 立场平衡复盘段空转」。
深查后：`council` **已在生产装配**（`config.council` + env 开关 + 后端注入），所以不是
「council 没接」。真缺口是**票的形状对不上**：

| 输入（council 实际产出） | 目标（nightwatch 要吃） |
|---|---|
| `AdvisorEvaluation { advisor, kind, verdict: AdvisorVerdict }` | `rubric::Ballot { advisor_id, stance: StanceKind, confidence: f64, weight: f64, domain }` |

`confidence` 与 `weight` **council 不产出**；且 `Ballot::new` **全仓从未被构造过**
（只有它自己的测试）。硬接必须**编造** confidence/weight ⇒ 我停下。

**选项**

| 选项 | 影响 |
|---|---|
| **A. 由 council 侧补出 `confidence`/`weight` 语义**（如 verdict 里的分数归一化为 confidence，weight 用顾问注册权重） | 票是真票，nightwatch 的立场平衡复盘**真的能跑**；代价：要定两个字段的语义（谁维护？改配置是否影响？） |
| B. 改 nightwatch 的输入类型，直接吃 `AdvisorEvaluation` | 不编造任何东西；代价：nightwatch 侧「立场平衡」算法要重写（它现在按 StanceKind 聚合） |
| C. 保持现状（nightwatch 继续报缺口） | 零成本；代价：这条复盘段永远空转 |

**我的建议**：**A**，且 `weight` 用现有顾问注册权重（council 已有 advisor 概念），
`confidence` 用 verdict 中的分数字段（若无则用 1.0 表示「无置信度信息」，并在票上标注
`confidence_defaulted=true`）—— 这样不编造、但也不阻塞。

**不裁定的后果**：这条自报缺口会一直在；「AI 评定 AI 的立场是否平衡」无从复盘。

## D-3｜`care_potential_field` 需要 distress / fatigue 信号源

**现状（证据）**

该模块的势能公式要三个输入：`distress`（挫败）、`fatigue`（疲劳）、`flow_resistance`。
**全仓 `grep` 无任何生产者**（除模块自身）。即：不是「模块没接线」，是**上游信号不存在**。

造信号 = 发明产品语义（什么算疲劳？深夜？连续失败？回合密度？），这是产品判断不是工程判断。

**选项**

| 选项 | 影响 |
|---|---|
| **A. 先定「最小可信信号集」**：例如 ①连续 N 次工具失败 = distress ②距上次成功交互时长 = fatigue ③（可选）本地时区深夜 | 有据可依、可实现、可测；但这是**产品定义**，需你点头 |
| B. 用 LLM 判断用户情绪 | 有既有情绪识别面吗？需查；且引入不确定性 |
| C. 保持未接（模块留着，不接） | 零成本；代价：这套「三阶克制关怀」永远不生效 |

**我的建议**：**先 A 的 ①②**（纯确定性、可测、不猜语义），③ 时区信号可后置
（涉及时区配置，W3.4 时区债还没收）。**不建议 B**（情绪判断不该由本模块自造）。

**不裁定的后果**：`care_potential_field` 及其势能公式永久闲置（它是生物机制族里
唯一「有完整实现但没有输入」的模块）。

## D-6｜问责闭环「后果追踪」缺自动回填

**现状（证据）**

ADR-0014 §5 第 ③ 步「后果追踪（`unknown` 一等公民）」目前**只有手动入口**：

```
apeireth egress outcome <ACTION_ID> <confirmed|failed>
```

`AccountabilityLedger` 的生产写入方只有 egress 闸（发信时落影响声明）；
行动跑完后**没有任何东西回填结果**，账面永远停在 `Outcome::Unknown`。

**为什么不硬接（两个硬障碍）**

1. **`confirmed` 不能自动填**：它的语义是「影响已按声明发生」，需要**外部证据**
   （对方是否真收到 / 副作用是否真出现）。本地工具调用成功 ≠ 影响已确认 ——
   自动填就是替外部背书。
2. **id 空间不对齐**：影响声明带 `action_id`（egress 闸产出），工具调用带 `ToolCall.id`；
   两者**没有既有映射**。

**选项**

| 选项 | 影响 |
|---|---|
| **A. 定「行动↔影响」归属语义 + 只自动填 `failed`** | 确定的错误能自动记账（工具调用出错 ⇒ 影响没发生）；`confirmed` 仍留人工/外部 |
| B. 只做「提醒」：超期 `unknown` 在 `apeireth egress impact` 里高亮 | 零风险，但仍是手动 |
| C. 保持现状 | 账面长期 `unknown`，问责链断在最后一步 |

**我的建议**：**A 的第一步 + B 同时做**：先做 B（超期 unknown 高亮，零风险、马上可用），
A 需要你先定归属语义（1:1？1:N？跨会话怎么算？）。

**不裁定的后果**：ADR-0014 的问责五步实际只走完四步；「后果追踪」停在手动。
