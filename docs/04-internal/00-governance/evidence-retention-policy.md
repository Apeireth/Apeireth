# 证据与产物留存策略（artifacts / reports / logs / previews / release-assets）

- **Status**: Accepted（owner 2026-10-22 裁定「不纳入 git」；2026-10-23 落地清理）
- **Date**: 2026-10-23
- **范围**: 仓库工作树里的过程证据 —— 测试日志、审计报告、调研稿、截图源件、发布资产草稿

## 1. 裁定

**过程证据不入 git。** 只把「结论」入库（文档、台账、claims、测试），不把「过程」入库。

理由（按重要性排序）：

1. **重复**：批量迁移过来的证据已完整保存在仓库外的证据归档（`Apeireth-evidence-2026-08~`），
   入库等于同一份字节存两遍；
2. **成本**：实测一个批次就会带进 230 个文件 / 185MB；此后每次 clone、每次 CI 拉取都要付；
3. **性质**：日志与截图的寿命以天计，代码的寿命以年计 —— 混在同一条历史里，
   会让 `git log` 变成噪音；
4. **风险**：大量未跟踪文件会让 `git add -A` 变成误提交陷阱。

## 2. 现在的实际状态（2026-10-23）

- 工作树**零未跟踪文件**：230 个未跟踪证据已移出仓库（其中 229 个与仓库外证据归档
  `Apeireth-evidence-2026-10-22/` 逐字节相同，1 个 `VCP-MEMORY-SYSTEM.md` 已补进该归档），
  零丢失；
- `.gitignore` 既有规则继续生效：`artifacts/*.png`、`artifacts/*.txt`、`/logs/`、
  `release-assets/`、`previews/*.png`（LFS）等 —— 这些**已跟踪**的历史文件保持原样，不迁移；
- 仓库内仍被跟踪的 `artifacts/`、`reports/`、`previews/` 文件是**历史交付物**，
  不因本策略回溯删除。

## 3. 纪律（对新批次）

1. 新产生的日志/截图/审计稿 → 一律写进**仓库外**的证据目录（建议
   `~/Projects/apeireth-evidence-<批次日>/`），不进仓库；
2. 需要入库的只写「结论」：`docs/` 下的文档、`docs/status/claims.yaml` 的 claim、
   测试用例本身；
3. 若某份证据确实必须入库（例如作为合规留痕），在 PR 里单独说明理由并按文件清单入库，
   不做整目录 `git add`；
4. 合并后自动删分支已开启（`delete_branch_on_merge = true`），战役分支不再堆积。
