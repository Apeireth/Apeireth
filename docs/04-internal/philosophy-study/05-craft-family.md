## §1 创作引擎簇（[artcraft](https://github.com/storytold/artcraft) · [photocraft](https://github.com/storytold/photocraft) · [vectorcraft](https://github.com/storytold/vectorcraft) · [effectcraft](https://github.com/storytold/effectcraft) · 非破坏性面 [lightcraft](https://github.com/storytold/lightcraft)）

> 取材=各仓 README 前 80 行实质内容（2026-10-18）；性能数字均为**对方自述口径**，未由本方复测。
> 簇定位：artcraft 是「AI 图像/视频创作 IDE」（2D 合成 + 3D 舞台 + 多模型目录），photocraft/vectorcraft/effectcraft/lightcraft 是同族单科应用，共用一套架构信条。

### 卡 1-1 · 多后端渲染管线 + 适配器自动降级

- **机制名**：多后端渲染管线 + 适配器自动降级（无 GPU 环境的正面回答）。
- **解决什么**：创作工具渲染重负载，但用户硬件谱系从核显、远程桌面到浏览器不等——GPU 加速与「机器没有像样 GPU」必须共存。
- **怎么设计**：渲染统一走 wgpu 抽象（Metal/Vulkan/DX12/WebGPU 后端并列）；photocraft 的合成器在 GPU 上跑（copy-on-write 瓦片 + 多线程滤镜）；vectorcraft 把 SIMD 渲染放 UI 线程外（自述 2 万形状约 27ms、界面保持 120fps）；**适配器策略显式化**：双显卡机器默认用省电核显、首选项/环境变量可按名字选卡、**一张卡带不动窗口就自动换下一张重启**；同一代码库经 wasm 进浏览器（wordcraft「native egui on the GPU、无 Electron」同源）。
- **设计哲学**：GPU 是加速层不是地基——「没有 GPU」被当成一等运行环境设计，而不是报错退出。
- **工程取舍**：弃旗舰卡峰值（默认核显=让掉部分性能）换全硬件谱系可运行；自动换卡要重启=以会话可持久化为前提。
- **我们现状→进步空间**：我们无渲染管线产品面 → 未来任何 GPU 加速面立项时把「适配器选择 + 自动降级 + 软件回退」写进第一版契约（默认核显、按名选卡、带不动换卡重启三件套）。

### 卡 1-2 · 命令注册表统一驱动面

- **机制名**：命令注册表统一驱动面（一引擎四出口）。
- **解决什么**：同一动作要同时服务人、脚本、自动化、agent；菜单/快捷键/CLI/JSON 控制通道/MCP 若各写一套，能力面必然漂移。
- **怎么设计**：**每个动作=带 id 的命令**，进唯一命令注册表：photocraft 自述「Every action is a command」；wordcraft 422 条命令同时驱动功能区、快捷键、命令搜索、CLI、JSON 控制通道、MCP server；deckcraft 200+ 条命令带撤销；vectorcraft 自家示例文档全部由命令 API 造出（示例=命令面的回归测试），README 明说菜单项/工具手势/面板/对话框皆可被驱动；lightcraft README 里的截图由 agent 经控制通道自动拍摄。
- **设计哲学**：「一个引擎、多个出口」——人类界面只是命令面的又一个消费者（与我们设计第一律同构，这是外部实证）。
- **工程取舍**：弃界面直连业务的短路径（一切动作绕注册表=多一跳）换能力面可被 agent 全量驱动；代价是命令命名/幂等/撤销语义升格为公共契约。
- **我们现状→进步空间**：我们 model 面 tool.* 是 AI 出口、CLI 是人出口、两套内核并存 → 动作统一进带 id 的命令注册表，人类界面=注册表的包装出口——「删掉人类界面能力仍完整」判据天然成立。

### 卡 1-3 · 撤销重做三形态

- **机制名**：撤销重做三形态（结构共享 / COW 快照 / 命名历史步）。
- **解决什么**：创作动作高频、文档大，撤销既要近乎免费又要能走回头路。
- **怎么设计**：vectorcraft 用**结构共享**持久数据结构撑「unlimited undo」；gridcraft 用 **copy-on-write 工作簿**（撤销快照近乎免费）；photocraft 给完整历史 + Toggle Last State（对比看上一步）+ History Brush（局部回刷任一步）+ 笔触确定性可重放；pdfcraft 的历史步可前后走、撤销项命名（「Undo Rotate pages」）、**保存之后撤销仍有效**。
- **设计哲学**：先定撤销的成本模型：记命令反做 vs 存状态差 vs 持久结构，按数据形态选。
- **工程取舍**：结构共享换内存常驻多版本；COW 换写放大控制；命名历史步换 UI 复杂度。
- **我们现状→进步空间**：我们动作面无统一撤销语义 → 新对象模型一律带「结构共享或 COW」撤销底座，撤销步命名且可前后走。

### 卡 1-4 · 非破坏性编辑栈

- **机制名**：非破坏性编辑栈（参数化 + 数据模型级不变量）。
- **解决什么**：用户要试错、要回头改早期决定，原物不能被覆盖。
- **怎么设计**：lightcraft 全参数化调整（自述原始文件永不动），scene-referred 宽色域 32 位浮点管线；mask 组件化（加/减/交 + 反相，每 mask 15 项局部调整 + 总强度），预设带 0–200% 强度滑杆；**色调曲线构造上单调**——把「不许意外反相」写进数据类型而不是靠检查；photocraft 同构：调整图层/智能对象/智能滤镜（滤镜可改可关可重排可 mask）。
- **设计哲学**：非破坏性不只是「不覆盖文件」，是把每个意图保留为可改参数；结构不变量由文档模型保证。
- **工程取舍**：全链路宽色域浮点算力×存储换可逆性。
- **我们现状→进步空间**：与我们「结构前置」同魂 → 任何新对象模型带两条硬规矩——原物不可变、不变量进数据类型（如单调曲线），参数可整组开闭。

### 卡 1-5 · 格式兼容层三件套

- **机制名**：格式兼容层三件套（公开规范 + 语料回归 + 显式降级）。
- **解决什么**：读写别人家格式是长期承诺，错一处毁一份用户文档。
- **怎么设计**：photocraft 的 PSD 支持独立 crate、按**公开规范**实现、对真实语料库回归（自述 307/309 测试文件渲染保持）；vectorcraft 原生格式=文档化 JSON（可干净 diff），round-trip 走 property test；gridcraft 以 XLSX 为原生格式全量 round-trip，XLSB/ODS 导入**显式降级**（取存值弃公式，边界写明）；pdfcraft 组合/拆分保完整性不变量（链接与命名目标重接、表单仍可交互、图层保默认、附件随行、逐页像素一致）。
- **设计哲学**：兼容性是资产不是功能——语料 + property test 当回归网；做不到的显式声明降级。
- **工程取舍**：语料库是前期投入；显式降级=承认边界，换用户可预期（诚实纪律的格式版）。
- **我们现状→进步空间**：我们导入面薄 → 格式层立「公开规范实现 + 语料回归 + 降级显式声明」三件套规矩。

## §2 文档模型簇（[wordcraft](https://github.com/storytold/wordcraft) · [gridcraft](https://github.com/storytold/gridcraft) · [pdfcraft](https://github.com/storytold/pdfcraft) · [deckcraft](https://github.com/storytold/deckcraft)）

> 取材=各仓 README 前 80 行实质内容（2026-10-18）；性能数字为对方自述口径。本簇是「结构前置」假说的实证源：结构化对象模型直接买来增量计算、继承一致性、可校验保存。

### 卡 2-1 · 增量布局引擎

- **机制名**：增量布局引擎（缓存 + 按需分页 + 虚拟化 + 依赖图重算）。
- **解决什么**：百页文档打字延迟、大表格滚动、多页渲染都要跟手。
- **怎么设计**：wordcraft 段落布局缓存，自述 188 页文档敲字局部重排约 1.4ms、页面按需渲染；gridcraft 依赖图计算引擎 + 动态数组溢出 + **增量重算**（只算脏格）+ **虚拟化网格只布局屏幕内**；pdfcraft 大页瓦片渲染（深缩放保持锐利）+ 每页渲染隔离。
- **设计哲学**：布局成本按「受影响范围」计费、不按「文档大小」计费——只有结构化文档模型拿得到这个粒度。
- **工程取舍**：缓存失效与依赖追踪的复杂度换交互延迟。
- **我们现状→进步空间**：「结构前置」的实证——结构化=可增量 → 知识对象模型按「脏标记 + 依赖图 + 增量重算」设计，整编浅接的下一层。

### 卡 2-2 · 继承式文档对象模型

- **机制名**：继承式文档对象模型（母版→版式→占位符→实例）。
- **解决什么**：几十页演示稿共用版式，改一处要全局生效，个别页又要例外。
- **怎么设计**：deckcraft 母版 + 11 种版式，占位符**继承位置与格式**，主题带配色/字体方案；wordcraft 样式集/主题/实时样式画廊，样式可建/改/更新、格式刷跨对象；gridcraft 结构化表引用（表名-列名寻址），公式脱离单元格坐标。
- **设计哲学**：文档对象模型的核心是「继承 + 可覆盖」，不是「复制 + 改」。
- **工程取舍**：继承链解析与覆盖优先级是复杂度来源，换全局一致性与改版效率。
- **我们现状→进步空间**：我们知识对象多为平铺结构 → 对象模型引入「模板→实例」继承（属性可被实例覆盖），结构前置的对象形态。

### 卡 2-3 · 导入导出组织

- **机制名**：导入导出组织（原生格式锚 + 异格式能力矩阵 + 共享组件裁剪）。
- **解决什么**：格式交换面是长期承诺，能力边界不说清就会被误用。
- **怎么设计**：wordcraft 以 .docx 原生读写（在主流办公套件可打开）为锚，其余格式带能力矩阵（rtf/odt/html/md/tex/txt 读写、旧版格式只读、PDF 导出带真文本/链接/书签）；deckcraft .pptx 读写 + PDF/PNG/GIF 导出，**共享 PDF 写入组件按功能面裁剪**（只启写入面、关闭导入面）；wordcraft README 附「诚实逐区清单」指到 ROADMAP。
- **设计哲学**：原生格式=兼容性锚；异格式=带能力声明的边缘面。
- **工程取舍**：feature 开关让应用只背需要的面；矩阵维护是持续成本，用诚实清单管理。
- **我们现状→进步空间**：我们的交换面在建 → 格式能力矩阵文档化 + 共享组件按面裁剪 + 「诚实清单」制度。

### 卡 2-4 · 可信保存与故障隔离

- **机制名**：可信保存与故障隔离（三性保存 + 每页隔离 + 崩溃恢复）。
- **解决什么**：文档应用最不可原谅的是丢数据、坏文件崩进程。
- **怎么设计**：pdfcraft 保存三性——**增量**（原字节逐字不动）、**原子**（临时副本写好再换入）、**独立校验**（CI 用独立工具逐构建验证）；每页渲染隔离、坏文件修复（自述 983 文件语料 0 崩溃）；每分钟 autosave、意外退出下次打开提供恢复、加密文档落盘保持加密；deckcraft 崩溃守卫的 panic 报告与恢复落日志、AutoRecover、日志轮转（两代 + 16MiB 上限、实时音频回调不打日志）。底层 craft-atomic：同目录暂存 + 目录 fsync + F_FULLFSYNC 兜底 + 瞬态锁退避 + **故障注入测试**。
- **设计哲学**：信任是测出来的——写路径每一步都要在故障注入下活下来。
- **工程取舍**：增量保存换文件增长（需压实策略）；独立校验换 CI 时间。
- **我们现状→进步空间**：我们有原子写意识但无故障注入制度 → 持久化统一走「暂存 + fsync + 换入」底座，关键写路径配故障注入测试。

### 卡 2-5 · 文档内寻址收口

- **机制名**：文档内寻址收口（craft-docpath：文档带的路径默认不跟）。
- **解决什么**：外来文档内嵌寻址是越权读取/外带面，「文档里存的路径/URL 能不能打开」必须有明确答案。
- **怎么设计**：craft-docpath 独立成 crate——文档内存储的路径**只在「本地」或「本文档自己所在的网络共享」两种情形下才跟随**；其余网络路径、设备路径、非 file URL 一律拒绝。
- **设计哲学**：文档是不可信输入，其携带的寻址能力默认收口。
- **工程取舍**：弃「点了就开」的顺滑（合法外链要用户手动）换越权面收口。
- **我们现状→进步空间**：三洋葱 + 写总闸管自家动作面 → 对外部输入携带的寻址指令立「默认不跟随」策略（对象级判定 G3 的输入面场景）。

## §3 AI 集成簇（[craft-ai-integrations](https://github.com/storytold/craft-ai-integrations) · 契约面延伸至 [craft-libs](https://github.com/storytold/craft-libs)）

> 取材=README 全文（68 行，未及 80 行上限，2026-10-18）。这仓与我们 provider 面**同题**：connections / keys / providers 的组织法。
> 仓内自述状态：契约「提议并入共享库仓、评审完成前为预备期」，README 明示「Nothing here is a final API」。

### 卡 3-1 · 契约先行分层

- **机制名**：契约先行分层（纯契约 core + 运行时半层 + 预备期身份）。
- **解决什么**：多应用 × 多提供方接入，接口漂移会把每个消费方拖下水。
- **怎么设计**：纯契约 crate（connections、capabilities、requests、jobs、consent、共享存储格式）**serde-only、无 IO、无异步运行时、可编译 wasm**，只含数据模型与提供方 trait；运行时半层（适配器/密钥库/应用侧客户端/本地运行时/可复用 UI 组件）另仓；契约「提议并入共享库仓、评审完成前预备期」的身份显式成文（README 明示「Nothing here is a final API」）。
- **设计哲学**：接口先冻结成纯数据契约、实现随便换；预备期不给消费方虚假稳定预期。
- **工程取舍**：序列化边界成本换跨目标（wasm/桌面）复用与独立评审；「不承诺 API」换评审自由度、增集成方跟进成本。
- **我们现状→进步空间**：我们 provider 面在建 → provider 契约独立成纯数据层（无 IO、可序列化、可离线校验），稳定性分级显式声明。

### 卡 3-2 · 连接 / 密钥 / 提供方三面组织

- **机制名**：连接 / 密钥 / 提供方三面组织（一次配置全族复用）。
- **解决什么**：接入配置散落各应用=重复劳动 + 漂移。
- **怎么设计**：连接面 ConnectionManager + 提供方注册表（ProviderFactory，各适配器注册）；密钥面三形态存储（OS 钥匙串 / 口令加密文件 / 环境变量）由桌面层统一持有；**工具→模型绑定**（ToolDesk：哪个工具走哪个模型）+ 模型选择器组件——用户在启动器或任一应用配一次、全族应用直接受用；官方建议不合适时**自定义连接/模型源/工具路由可插入**。
- **设计哲学**：接入层是全族共享设施不是应用私产；「用户自带接入路径」是一等公民。
- **工程取舍**：共享绑定换一致性（换模型全族生效）；三形态密钥库换平台差异复杂度。
- **我们现状→进步空间**：与我们 provider 面同题 → 连接/密钥/绑定三分离；密钥库以钥匙串优先、加密文件兜底；用户自定义 provider 路由显式开面。

### 卡 3-3 · 同意与作业面

- **机制名**：同意与作业面（status / plan / consent / start / Job + history）。
- **解决什么**：模型调用花钱、动数据，用户须知情「要做什么、做过什么」。
- **怎么设计**：应用侧客户端对象五件套——status、plan、consent、start、Job：先看状态与计划、用户同意后启动、作业对象跟进度；同意与历史落文件持久化；UI 组件族带同意提示与作业进度（主题中立）。
- **设计哲学**：AI 调用是「请求-批准-执行-留痕」事务，不是普通函数调用。
- **工程取舍**：每次调用多一步同意（可批量授权补效率）换花钱动作的知情权。
- **我们现状→进步空间**：我们审批四态 + 三维预算同题 → 模型面调用统一「plan 先行 + consent 分级 + Job 留痕」，plan 给预估、与预算闸联动。

### 卡 3-4 · 模型目录与出处账本

- **机制名**：模型目录与出处账本（size / SHA-256 / 来源 / 许可 / 缺口自报）。
- **解决什么**：本地模型散落各处、来源不明、版本混乱，「这台机器能跑什么」不可见。
- **怎么设计**：AI 工具目录（wasm-safe）登记每个工具：出现在哪、本机怎么跑（模型文件带**大小、SHA-256、来源、许可**）、**本机还缺什么**；引擎面=「运行器契约 + 一个在本机跑任何已注册模型的提供方」；环境清点器：发现已有安装、清点模型文件与节点包、补下缺失模型。
- **设计哲学**：模型是依赖不是素材——进目录、校验哈希、记出处、报缺口。
- **工程取舍**：哈希/出处登记换清单维护成本；缺口自报换用户可预期。
- **我们现状→进步空间**：我们模型文件资产未成面 → 大文件资产立「清单 + 哈希 + 来源 + 许可 + 缺口自报」账本。

### 卡 3-5 · 接入层自身的防御与诚实面

- **机制名**：接入层自身的防御与诚实面（统一 TLS + 媒体留存 + panic 禁令 + 已验证清单）。
- **解决什么**：托管调用/下载是出口面，库 panic 是稳定性地雷，「哪些真跑过」不能含糊。
- **怎么设计**：统一 HTTP 出口——全部托管调用与下载共用**一个 TLS 设置**（平台证书校验）；托管媒体链接本地留存（durable copies + 校验）；库层规矩：no unsafe + 发布代码 deny unwrap/expect/panic；CI 全套（fmt / clippy / wasm check / 双平台测试 / cargo-deny）+ 真钥匙串测试显式 `#[ignore]` + **变异测试工具**（故意埋 bug 验证测试有效性）；README 立「已验证 / 未验证」清单（未验证项明列：真实托管服务、拦截代理下的 TLS、非本机平台钥匙串等）。
- **设计哲学**：库的失败模式要可预期（禁 panic）；能力可信度=已验证清单的诚实度。
- **工程取舍**：deny panic 换错误处理样板；变异测试换 CI 时间；明列未验证项换「看起来不完美」。
- **我们现状→进步空间**：与我们 0 装诚实纪律同魂（对方给了库级实现法）→ 库层 deny panic 制度化、出口 TLS 收口、能力面配「已验证/未验证」清单 + 变异测试进 CI。
