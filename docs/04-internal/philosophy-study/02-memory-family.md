## 1. aiming-lab/SimpleMem（终身记忆结构）

> 引注用途：长生命周期记忆的原子化组织与检索基础设施。取材=README 装饰层后的前 80 行实质内容（jsdelivr 镜像，因 API 限流与 raw 端点故障）。

### 卡 1-1 · 原子化记忆抽取 + 语义无损压缩

- **机制名**：原子化记忆抽取 + 语义无损压缩。
- **解决什么**：对话流与事实流直接堆入上下文，导致冗余复算、窗口溢出、跨会话遗忘。
- **怎么设计**：写入路径固定三步——①抽取：对话/事实被整理为结构化的原子记忆条目；②索引：以语义嵌入与结构化元数据组织；③检索：按含义相关度而非措辞命中召回。存储侧以"语义无损"作为压缩准则（压缩后语义可复原，非字节可复原）；多模态输入走统一入口，按首个调用形态自动路由到文本或多模态后端。
- **设计哲学**：记忆的最小单位应是原子事实，压缩的底线是语义保真而非字面保真。
- **工程取舍**：语义无损换取检索精度与可复原性，代价是写入期需要模型参与的抽取与判定开销。
- **我们现状→进步空间**：已有压缩检查点 + 双时态事实流 → 把"语义无损"写成压缩检查点的显式验收判据（可机器检验），并把原子化抽取前置到写入路径，而不是留给压缩阶段兜底。

### 卡 1-2 · 语义嵌入 + 结构元数据的双通道索引

- **机制名**：语义嵌入 + 结构元数据的双通道索引。
- **解决什么**：措辞不同但含义相同的查询召回不到既有记忆，关键词通道天然漏检。
- **怎么设计**：索引层同时维护语义向量与结构化元数据两路通道；检索入口按"意思"匹配，并通过通用协议接口对任意客户端开放记忆能力，使记忆层与智能体运行时解耦。
- **设计哲学**：检索的单位是含义，索引要同时回答"像什么"与"是什么"。
- **工程取舍**：双通道提升召回鲁棒性与可移植性，代价是索引存储翻倍与两路一致性维护。
- **我们现状→进步空间**：五层混合检索已有骨架，但图谱/向量未真生产 → 先把元数据通道做实（可独立于向量上线、立即见效），向量通道随后增量补课，避免两路同时悬空。

### 卡 1-3 · 检索基础设施的自进化闭环

- **机制名**：检索基础设施的自进化闭环（该项目 EvolveMem 线）。
- **解决什么**：检索维度是设计期定死的静态集合，覆盖不了事后出现的查询形态，能力上限被设计者想象力锁死。
- **怎么设计**：模型驱动的闭环持续运转——评测检索表现→诊断失败模式→自行提出此前设计中不存在的新检索维度→回灌评测集复测；以标准记忆评测集报告相对增益，用数据而非直觉决定维度是否留下。
- **设计哲学**：检索结构不应是设计期常量，而应是运行期可被证据改写的变量。
- **工程取舍**：自进化抬高能力上限，代价是系统行为可变性上升，必须配回归门槛防止"进化"变"退化"。
- **我们现状→进步空间**：教训回路已有但仅整编浅接 → 让教训回路的产出落到"检索维度新增"这一显式动作上，并以回归基准为放行门槛，形成可审计的进化记录。

## 2. Atuin/Atuin（历史即记忆）

> 引注用途：把命令历史当作结构化记忆体的工程范式。取材=README 前 80 行实质内容（全文实质仅 66 行，经 jsdelivr 镜像取回）。

### 卡 2-1 · 上下文富化的事件历史库

- **机制名**：上下文富化的事件历史库（历史即记忆）。
- **解决什么**：传统命令历史只是纯文本行流，无法回答"何时、何处、哪次会话、是否成功、耗时多少"这类回溯问题，记忆缺少可推理的结构。
- **怎么设计**：每条命令被记录为带上下文的结构化事件——时间戳、退出状态、工作目录、主机、会话标识、耗时等元数据随行入库，统一落在本地单文件数据库（SQLite）中；既有历史文件不被替换，而是经导入通道摄取为同构事件；另提供统计视图（如高频命令）。
- **设计哲学**：记忆的价值不在文本本身，而在附着于文本的时空、场景与结局上下文。
- **工程取舍**：结构化事件化增加写入钩子与模式维护成本，换来可查询、可统计、可跨终端复用的记忆体。
- **我们现状→进步空间**：双时态事实流已具备事件时态 → 给教训/操作记录补齐"结局与场景维度"（成功与否、发生场景），使教训回路能按结局过滤，而非只按主题检索。

### 卡 2-2 · 作用域优先的检索面

- **机制名**：作用域优先的检索面（会话/目录/全局三档 + 属性条件）。
- **解决什么**：全局历史检索噪音极大；用户真正想问的通常是"在我当前的场景里发生过什么"。
- **怎么设计**：检索入口把作用域做成一等过滤器——当前会话、当前目录、全局三档一键切换，其上再叠加属性条件（成功/失败、时间窗、关键词）；交互上以全屏搜索界面承接高频回溯，回车执行、制表编辑，把"检索—复用"压成一步。
- **设计哲学**：记忆检索的第一维应是场景作用域，关键词只是最后一维。
- **工程取舍**：作用域过滤要求写入期可靠保留场景字段，钩子复杂度上升；换来的是检索噪音的结构性下降。
- **我们现状→进步空间**：五层混合检索尚未显式建模场景作用域 → 把"当前任务/目录/会话"设为检索的第一层预过滤，再进五层通道，预期显著降噪。

### 卡 2-3 · 本地优先的密态同步层

- **机制名**：本地优先的密态同步层（跨终端/会话/机器一致的记忆）。
- **解决什么**：记忆要在多终端、多会话、多机器间保持一致，但集中托管会带来内容暴露面扩大。
- **怎么设计**：本地数据库是记忆的第一公民，同步是可选附加层；客户端完成加密后仅上传密态副本，托管侧只保存不可读数据；用户可在托管服务、自建服务、不同步三者间自由选择。（加解密实现细节不展开，只取架构结论。）
- **设计哲学**：记忆的主权在本地，同步只搬运密态副本。
- **工程取舍**：密态同步放弃服务端检索与服务端智能，换取信任最小化与部署自由度。
- **我们现状→进步空间**：记忆存储尚无主权拓扑设计 → 明确"本地优先、同步可选"的存储拓扑，把敏感记忆的加密边界写入架构约束，而非留给实现期决定。

## 3. volcengine/OpenViking（自进化上下文）

> 引注用途：以虚拟文件系统组织智能体全部上下文（知识/记忆/技能）的数据库化路线。取材=README 前 80 行实质内容（raw 端点，本次链路恢复）。

### 卡 3-1 · 虚拟文件系统式上下文组织

- **机制名**：虚拟文件系统式上下文组织（可检视、可编辑的记忆库）。
- **解决什么**：智能体记忆常是黑盒——写入文本、产出嵌入，实际存了什么无从查看；知识、记忆、技能三类上下文各存各的，形态割裂。
- **怎么设计**：全部上下文挂在一个虚拟文件系统命名空间下（自有 URI 方案，可寻址到任意条目），统一三类上下文：资源（文档/代码）、记忆（偏好/经验）、技能（任务做法）；操作面复用文件原语（列目录、树览、读、写、检索），任何目录都可打开人工检视与编辑。
- **设计哲学**：记忆应当像文件系统一样可被打开、检视和手改，透明性是记忆可信的前提。
- **工程取舍**：文件系统隐喻牺牲了部分数据库级的查询效率与约束能力，换来人机共用的统一心智模型与可调试性。
- **我们现状→进步空间**：双时态事实流是内部结构、外部不可检视 → 为记忆/教训/技能提供统一的可寻址命名空间与人工检视入口，把"可检视性"作为记忆子系统的验收属性。

### 卡 3-2 · 摘要先行的三层渐进加载 + 作用域检索

- **机制名**：L0/L1/L2 三层渐进加载，配套目录作用域检索。
- **解决什么**：整库扁平向量检索既贵又噪；读全文才知道相关与否，上下文与延迟都被无关内容拖垮。
- **怎么设计**：每个语义化处理过的目录携带两层生成摘要——L0 一句话摘要用于快速相关性判断，L1 概览给出核心信息与适用场景用于规划，L2 才是按需加载的完整原文；检索入口区分两个动作：直查式检索（在给定目录内跑查询）与规划式检索（结合会话上下文先做检索规划再执行），语义检索被限定在目录子树内而非扫全库。
- **设计哲学**：先读摘要再读源；检索的第一决定是"在哪找"，第二决定才是"找什么"。
- **工程取舍**：摘要生成增加写入期成本，且摘要质量成为新的单点风险；换取输入令牌与查询延迟的大幅下降（其自报基准：输入令牌降 34.3–91.0%，延迟降约 58–66%）。
- **我们现状→进步空间**：五层混合检索 + 溢出取回已有，但缺"摘要先行"的廉价预判层 → 在各层之上补 L0/L1 式摘要门，先判相关再放行取回，把溢出取回的触发做成两段式。

### 卡 3-3 · 会话提交 → 记忆抽取 → 上下文编译

- **机制名**：会话提交与上下文编译（会话归档、记忆抽取、素材整编）。
- **解决什么**：会话结束即蒸发，或只留下不可读的向量残影；经验无法沉淀为可复用、可修订的知识制品。
- **怎么设计**：会话"提交"动作把对话归档为可读文件，并抽取出记忆——落成可检视、可编辑、可合并的文档形态；进一步的编译步骤把源素材整编为维基、知识图谱或报告等目标形态，即"同一素材、多种整编输出"。
- **设计哲学**：记忆应从会话中"编译"出来，成为可修订的一等制品，而非会话的副产品。
- **工程取舍**：抽取与整编需要模型多轮加工，有成本与漂移风险；换取经验的可读性、可合并性与跨任务复用。
- **我们现状→进步空间**：教训回路已产教训、整编仅浅接 → 把"会话提交"定义为显式生命周期事件，其产出直接喂给整编通道，并让整编产物（维基/图谱/报告）成为可选输出形态而非一次性转写。

## 4. thedotmack/claude-mem（记忆扩展）

> 引注用途：面向编码智能体的持久记忆压缩与跨会话续接扩展。取材=README 前 80 行实质内容（jsdelivr 镜像）。

### 卡 4-1 · 工具使用观察的自动捕获与语义摘要化

- **机制名**：工具使用观察的自动捕获与语义摘要化（捕获→摘要→召回闭环）。
- **解决什么**：会话一结束上下文即失；若靠人工记录，负担重且覆盖不全，连续性不可靠。
- **怎么设计**：经宿主集成点自动捕获工具使用事件（无钩子能力的宿主则改为监听其会话日志文件），对捕获内容生成语义摘要并写入持久层；新会话开启时自动把既往上下文接回来；捕获后端可切换——托管观察器、本地观察器或用户自带模型通道，记忆计算可与主模型计划解耦。
- **设计哲学**：记忆应是运行的副产品，好的记忆系统不让用户当记录员。
- **工程取舍**：自动捕获绑定宿主集成点与日志监听路径，集成面广、适配成本高；换来零手工负担与会话连续性。
- **我们现状→进步空间**：教训回路偏事后整编 → 把捕获前移到工具调用层做自动观察采集，整编阶段只做去重、提纯与合并，降低对"事后回忆"的依赖。

### 卡 4-2 · 渐进披露检索（分层召回 + 成本可见）

- **机制名**：渐进披露检索——分层召回且令牌成本可见。
- **解决什么**：把旧上下文全量注入烧窗口；一刀切式召回要么漏关键信息，要么把上下文撑爆。
- **怎么设计**：召回按层递进，每一层的令牌代价对调用方可见，由调用方在成本知情的前提下决定是否加深；配套把查询封装为可复用的检索技能入口，并提供实时记忆流观察界面，让"存了什么、召回了什么"可观测。
- **设计哲学**：召回深度应是运行期可调的旋钮，且每挡旋钮的代价必须可见。
- **工程取舍**：分层接口与成本回传增加设计复杂度，换取上下文预算的可控性与可解释性。
- **我们现状→进步空间**：溢出取回已有分层思想，但取回成本不显式 → 把每层取回的令牌成本显式回传调度器，形成预算感知的召回深度控制。

### 卡 4-3 · 针尖观察推送 + 显式排除标记（选择性记忆）

- **机制名**：针尖观察推送 + 显式排除标记。
- **解决什么**：并非所有内容都值得入记忆；关键决策与修复记录需要优先浮现，而另一些内容应当根本不出库。
- **怎么设计**：定义少量高价值观察类别（如决策、修复记录、警示类条目），命中即生成带日期的简短条目，推送到下游已有的日志通道并复用其回读机制，形成"感知推送"；同时提供显式排除标记，标记范围内内容不进入存储；注入哪些上下文可按配置细粒度裁剪。
- **设计哲学**：记忆系统既要会"记"，也要会"不记"；价值密度靠类别白名单前置筛选，而非事后全文捞取。
- **工程取舍**：类别白名单需持续维护、类外价值可能漏记；换取低噪音召回与可控的内容暴露面。
- **我们现状→进步空间**：保护遗忘曲线解决"留多久"，但缺"进不进"的前置分类 → 在写入路径加价值分类门（高价值直推、排除标记即拒），与遗忘曲线构成进出双向控制。

## 5. virgiliojr94/book-to-skill（知识→技能）

> 引注用途：把成册知识蒸馏为可按需加载的技能制品的转换范式。取材=README 前 80 行实质内容（jsdelivr 镜像）。

### 卡 5-1 · 一次性结构化蒸馏，换恒定查询开销

- **机制名**：一次性结构化蒸馏（结构优先，非摘要优先）。
- **解决什么**：整本资料直接倒进上下文，每一轮都要重复"取目录—回溯—重解析"的发现环开销；事后检索只给页码不给答案；读完即忘、笔记无人再看。
- **怎么设计**：转换期一次性付出结构化成本，把资料蒸馏为框架、决策规则、反模式与分章文件——产物是结构而非缩写；查询期开销与答案规模成正比，而非与资料规模成正比（其自报实测：比全文入上下文省 24×–51× 令牌）。
- **设计哲学**：知识的整理成本应该在转换期一次性付清，让每次查询只花与答案成正比的钱。
- **工程取舍**：转换期需要多轮加工与质量校验，是前置重投资；换来查询期的恒定低开销与答案可溯源到原文。
- **我们现状→进步空间**：压缩检查点解决窗口压力，但未把"整理成本一次付清"作为显式预算策略 → 对反复回看的资料集做一次性蒸馏制品，明确"转换期重、查询期轻"的成本曲线。

### 卡 5-2 · 令牌预算化产物 + 按需章节加载

- **机制名**：令牌预算化产物 + 按需章节加载。
- **解决什么**：单一长文档要么全量加载撑爆预算，要么切太碎导致检索不到全局；制品大小不可预期。
- **怎么设计**：产物是一个制品族，每个文件都带显式令牌预算——核心文件（心智模型 + 章节索引，约数千令牌）常驻；各章文件（每份约千级令牌）按需加载，未被问及不占预算；另有术语表、模式集、速查表三类横向制品分别承接"查词、查做法、查决策"三种问法。
- **设计哲学**：知识制品应按"问法"分形存储，预算写在文件契约里而不是事后估算。
- **工程取舍**：制品族与索引结构增加生成复杂度，且预算需随内容演化维护；换来可预期的上下文占用与问法直达。
- **我们现状→进步空间**：溢出取回有分层，但技能卡随手记尚在建、无预算契约 → 技能卡采用"核心卡 + 分章卡 + 横向卡"的制品族形态，每卡声明令牌预算，加载按问法路由。

### 卡 5-3 · 双半区管线 + 增量折入更新

- **机制名**：确定性提取器 + 规范驱动生成器的双半区管线，配增量折入。
- **解决什么**：单一模型端到端转换既不可复现也难定位错误；知识制品生成后很快过时，新材料来了只能整本重转。
- **怎么设计**：管线分两半——前半是确定性提取（文档→干净文本 + 元数据，按格式逐个尝试可用工具，缺失时明确告知补装路径）；后半是规范驱动生成（智能体按既定规范把提取结果组织为技能结构，保证跨宿主同构产物）；另有更新/折入模式，新材料落地时折入既有结构而非整体重建。
- **设计哲学**：确定性的事交给代码，组织化的事交给规范驱动的智能体；知识要能"折入"而不用"重炼"。
- **工程取舍**：双半区与规范维护增加工程量，换取可复现性、错误可定位与增量可维护性。
- **我们现状→进步空间**：整编浅接且一次性转写居多 → 把整编拆成"确定性预处理 + 规范化组织"两段，并把增量折入定义为整编的默认入口，重炼只作例外。

## 6. nashsu/llm_wiki（知识自动构建）

> 引注用途：文档自动整编为持续保鲜的结构化知识库的工程范式。取材=README 前 80 行实质内容（jsdelivr 镜像）。

### 卡 6-1 · 三层架构 + 三操作 + 人机角色分工

- **机制名**：原始层/维基层/规则层三层架构，配摄取—查询—校订三操作。
- **解决什么**：知识要么散在原始文档里不可用，要么被一次性摘要毁掉结构；生成内容与来源脱节后无法信任、无法维护。
- **怎么设计**：①原始层（来源文件，不可变）→ ②维基层（模型生成的维基页）→ ③规则层（结构规则与配置，另设"意图文件"声明这座库为何存在、关键问题与演化论点）；三操作循环：摄取、查询、校订；导航靠内容索引文件 + 可解析的操作日志文件，页间用双链互引，每页带元数据头（含来源列表字段），目录可直接当笔记库打开；角色分工是"人做策展、模型做维护"。派生视图层提供多信号关联图谱（直接链接、来源重叠、拓扑邻近、类型亲和）与社区发现、缺口洞察。
- **设计哲学**：来源不可变、生成可重建、规则可修订；人握方向，模型握维护。
- **工程取舍**：三层分离与元数据规约增加结构性约束，换来生成内容可追溯、可校订、可长期维护。
- **我们现状→进步空间**：双时态事实流有来源意识但缺"规则层/意图层"的显式文件化 → 把结构规则与方向意图落成可修订的声明式文件，让摄取与查询都以它们为条件输入。

### 卡 6-2 · 两步分析—生成摄取（矛盾检测 + 来源可溯 + 人工复核项）

- **机制名**：两步思维链摄取——先分析、后生成。
- **解决什么**：单步"边读边写"式摄取质量差：既错过与既有知识的关联，也看不见冲突；生成页无法回溯来源。
- **怎么设计**：摄取拆为两次顺序调用——第一步分析：抽取关键实体、概念、论点，找出与既有库的关联、矛盾与张力，给出结构建议；第二步生成：据分析产出来源摘要页、实体页、概念页（带互引），同步更新索引/日志/概览，并派生两类副产物：需人工裁决的复核项、供深研用的检索查询。每页元数据头强制携带来源列表，做到页→原始文件可回溯。
- **设计哲学**：先想清楚再落笔；摄取的副产物应包括"待人裁决的疑点"，而不是只产出顺滑文本。
- **工程取舍**：两步调用翻倍摄取成本、拉长入库延迟，换来冲突显式化、结构更优与来源可溯。
- **我们现状→进步空间**：教训回路有复核意识但未制度化 → 在摄取/整编管线里固定"矛盾检测 + 人工复核队列"两个出口，让冲突进入裁决流程而非被平均化抹平。

### 卡 6-3 · 保鲜机制族（增量缓存 + 持久摄取队列 + 源目录监视）

- **机制名**：编译一次、持续保鲜——增量缓存、持久队列、目录自动监视三件套。
- **解决什么**：每次查询都从零推导（传统检索式问答）既贵又不稳；库建成后新素材、修改、删除无法同步，知识库很快过期。
- **怎么设计**：①增量缓存：摄取前对来源做内容散列，未变动即跳过，省模型调用；②持久摄取队列：串行处理避免并发调用，队列落盘、崩溃可恢复、失败自动重试、可取消；③源目录自动监视：目录外部的增删改自动纳入同一套摄取/清理生命周期；向量检索开启时新页自动入库嵌入。核心立场：知识编译一次并持续维护，而不是每次查询重新推导。
- **设计哲学**：知识库的价值在"保鲜"，保鲜要靠幂等、可恢复的维护机制，而不是靠人记得重跑。
- **工程取舍**：队列与监视器是有状态服务，需处理崩溃恢复与幂等；换来运行成本随"变更量"而非随"查询量"增长。
- **我们现状→进步空间**：压缩检查点是时点动作，缺持续保鲜回路 → 引入内容散列增量门 + 可恢复的摄取队列，把"变更驱动的增量整编"作为常态路径。

## 7. mempalace/mempalace（记忆宫殿式检索）

> 引注用途：逐字保留 + 结构化分域索引的本地优先记忆路线。取材=README 前 80 行实质内容（raw 端点；项目存在，非"未获取"）。仿冒站点警示段落按纪律跳过，不纳入分析。

### 卡 7-1 · 逐字保留 + 零模型调用的语义检索

- **机制名**：逐字保留原文的语义检索（反摘要路线）。
- **解决什么**：摘要/抽取/转述式记忆会永久损失细节，且回答时把模型调用混进召回链路，带来成本、延迟与二次失真。
- **怎么设计**：对话历史以逐字文本存入，明确不做摘要、抽取或转述；检索层对原文做语义搜索，命中后以原文形态回供；召回链路不含模型调用（其自报基准：LongMemEval 原文检索 R@5 达 96.6%，零 API 调用）；配套"先召回再作答"的技能入口把检索固定为回答前置动作。
- **设计哲学**：记忆的第一职责是不走样——能不压缩就不压缩，把保真放在省token之前。
- **工程取舍**：逐字保留把成本推给检索侧（索引体积、检索精度要求高），换取无损细节与召回链路的确定性。
- **我们现状→进步空间**：压缩检查点默认"压缩是必然" → 对少量高价值事实流（关键决策、教训原文）设"逐字保留区"，绕过压缩直通检索，与压缩区形成保真分级。

### 卡 7-2 · 宫殿式分域索引（翼/室/屉三级）

- **机制名**：宫殿式分域索引——人物与项目成翼、主题成室、原文入屉。
- **解决什么**：扁平语料上的全局语义搜索噪音大、作用域不可控，检索无法按"找哪一块记忆"来收窄。
- **怎么设计**：索引被组织为三级空间结构——人/项目级的"翼"、主题级的"室"、承载逐字原文的"屉"；检索先选域再查义，作用域是一等公民，搜索在子结构内进行而非打扁平库。
- **设计哲学**：检索精度来自空间结构而非向量精度；先划边界再谈相关。
- **工程取舍**：结构维护需要入库时的归域决策（放错屉即检不出），换取可控的检索域与人可理解的布局。
- **我们现状→进步空间**：图谱/向量未真生产，作用域靠检索层临时裁剪 → 先把"域结构"（人物/项目/主题三级）做实为显式索引，向量只做域内排序，降低对向量精度的单点依赖。

### 卡 7-3 · 可插拔检索后端 + 本地优先边界

- **机制名**：后端接口化（默认实现可整体替换）+ 本地优先数据边界。
- **解决什么**：记忆系统被单一检索实现绑死则难以演进；数据外流使记忆资产脱离用户掌控。
- **怎么设计**：检索后端定义为显式接口，默认实现（某嵌入向量库）可被替代实现整体接换，其余系统不动；数据默认不出本机，外发须显式选择加入；面向编码智能体提供引导式安装、召回、任务委派三类技能入口，把运维也技能化。
- **设计哲学**：记忆资产留在本地，检索实现只是可替换的零件。
- **工程取舍**：接口抽象要求后端能力取最小公分母，可能牺牲个别实现的独有特性；换来可演进性、可迁移性与数据主权。
- **我们现状→进步空间**：图谱/向量绑定单一未生产化实现 → 为检索后端立最小接口契约，先接一个可用默认实现跑通生产，替代实现按需接入而不改上层。

## 8. 横向观察（一句话）

七个项目在三个轴上分野清晰：**压缩还是保真**（SimpleMem 语义无损压缩 ↔ mempalace 逐字不压缩）、**结构放在哪**（OpenViking/llm_wiki/book-to-skill 把结构前置到转换期，Atuin/claude-mem 把结构留在写入期元数据）、**记忆由谁维护**（llm_wiki"人策展模型维护" ↔ claude-mem 全自动捕获 ↔ mempalace 干脆不加工）。我们现有机制在三轴上均偏"写入期加工 + 压缩优先"，进步空间集中在**保真分级、结构前置、保鲜回路**三处。
