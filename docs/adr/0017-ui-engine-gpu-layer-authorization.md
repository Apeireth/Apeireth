## 1. 背景

ADR-0015 立项时，引擎的硬边界写得很清楚（§2.1）：

> 引擎只做三件事：响应式调度 / DOM 绑定 / 过渡时序。
> **不写 CSS 引擎、不写滤镜层、不碰 shader、不碰排版、不碰主题。**

同时它把 **GPU 场景**（生产的 `blackhole.ts` 1,037 行 / 2 条 GLSL）列为
「**零改写**」项 —— 即**生产那份**不动。

但后续实施里，**片头场景**（`intro/fire.ts` 的 1,000+ 行 GLSL 火焰）
被**搬进**了引擎侧（`crates-ui/apeireth-ui-scene/src/intro/**`，2,008 行）
⇒ ⇒ 于是产生了两个必须回答的问题：

1. 这算不算**越出** ADR-0015 的边界？
2. 如果不算，**授权范围**写在哪里、怎么防止边界继续被侵蚀？

### 1.1 owner 拍板（2026-10-27）

owner 在被问到「片头留在引擎还是退回生产侧」时的答复：**「留引擎呗」**。

⇒ ⇒ **片头留在引擎**是**已决策**状态，不是待议项。

### 1.2 决策当时给出的判据（本文固化之）

判断「某一层该不该接管」的三问（避免以后凭感觉扩张）：

| # | 判据 | 含义 |
|---|---|---|
| ① | 这层有立项的**三个真问题**吗？ | 不可测 / 契约漂移 / 双份维护 |
| ② | 接管后能给出**可判定的**等价判据吗？ | 不能 ⇒ 只能「量化 + 豁免」⇒ 那是永久的验收坑 |
| ③ | 接管后这件事**只剩一份实现**吗？ | 不是 ⇒ 收益被长期双份维护抵消 |

⇒ ⇒ **三问都过 ⇒ 接管；第 ② 问不过 ⇒ 最危险（不得接管）。**

### 1.3 逐层结论（按判据）

| 层 | ① 三病 | ② 可判定 | ③ 单一实现 | 结论 |
|---|---|:--:|:--:|---|
| `ui-core` 响应式 | 3/3 | ✔ | ✔ | 接管（已交付） |
| `ui-dom` 绑定 | 3/3 | ✔ | ✔ | 接管（已交付） |
| `ui-kit` 组件 | 2/3 | ✔ | ✔ | 接管（已交付） |
| GPU 场景骨架（wgpu） | 1/3 | 部分 | ✔ | 接管（**第二阶段原生窗口**的地基） |
| **片头火焰** | 1/3 | ⚠ **见 §3** | ❌ 双路径 | **接管（owner 拍板）** |
| CSS 主题 / 排版 / 滤镜 | 0/3 | — | — | **不接管**（ADR-0015 已明写） |

## 2. 决策

**片头 GPU 场景保留在引擎侧**（`apeireth-ui-scene/src/intro/**` + `apeireth-ui-gpu`），
并把「**引擎 GPU 层的授权范围**」显式写下来，**配套可执行守卫**。

### 2.1 授权范围（**白名单**）

| crate | 授权 |
|---|---|
| `apeireth-ui-core` | 响应式调度、派生、作用域（**0 shader**） |
| `apeireth-ui-dom` | DOM 绑定、事件、过渡时序（**0 shader**） |
| `apeireth-ui-kit` | 组件与主题令牌（**0 shader**） |
| `apeireth-ui-gpu` | ⭐ **着色器变换 / 渲染管线 / 设备管理 / 后端选择** |
| `apeireth-ui-scene` | ⭐ **场景、时间线、相机、intro 粒子场景** |
| `apeireth-ui-demo` | 试点组件与装置（**不自算时区**；见 §2.3） |
| `apeireth-ui-macro` / `ui-time` | 过程宏 / 时间文本宿主能力 |

### 2.2 **仍然禁止**（**黑名单**，与 ADR-0015 §2.1 一致）

- ❌ 在 `ui-core` / `ui-dom` / `ui-kit` 里出现**任何**着色器源码或 GPU 资产；
- ❌ 引擎写 **CSS 引擎 / 滤镜层 / 排版引擎 / 主题引擎**；
- ❌ 引擎碰 **HTTP / SSE 契约**或**能力门控**（那属于宿主与后端协议层）。

### 2.3 ⭐ 新增硬约束：**时间文本只有一个入口**

时间文本**一律**走 `apeireth_ui_kit::governance_tab::time_text()`
⇒ ⇒ 宿主在 wasm 上装 `apeireth_ui_time::install()`（浏览器 `Intl`）⇒ ⇒ 与生产**同一时区口径**。

⇒ ⇒ **组件不得**自带「固定 UTC」之类的自算实现
⇒ ⇒ 实测教训（2026-10-27）：审批卡曾自带 `format_clock_utc`
⇒ ⇒ 宿主**装了**浏览器 `Intl`，而该消费方**不消费**
⇒ ⇒ 非 UTC 时区下生产 `09:10` / 引擎 `01:10`（**差 8 小时**）。

### 2.4 ⭐ 守卫（**边界从文档变成会红的门禁**）

新增 `crates-ui/apeireth-ui-demo/harness/scripts/check_ui_boundaries.py`，进 CI：

- **守卫 A**：`ui-core` / `ui-dom` / `ui-kit` 内 **0** 着色器痕迹、**0** GPU 资产文件；
- **守卫 B**：`ui-demo` 的**组件**层不得引用自算时区实现。

⇒ ⇒ 豁免表与本文**同步维护** ⇒ ⇒ 任何扩大授权范围的改动
⇒ ⇒ 必须**同时**改本文与守卫 ⇒ ⇒ ⇒ 「授权」不再是口头约定。

## 3. 片头的等价判据（**第 ② 问的答案**）

片头「生产 vs 引擎」的差异实测 **12.04%**（冻结 2.5s）。
逐项排除后（详见台账 E-55 / E-57 / E-59）：

- uniform **数值零差异**（85/87 键）；种子 **16,384 分量全等**；
- 引擎**变换后的着色器**与生产源**逐行只差** `layout(location=N)` 与注释 ⇒ ⇒ **语义一致**；
- `probe=flat`（把粒子片元换成纯色）下**几何逐像素 0 差异** ⇒ ⇒ **位置与尺寸一致**；
- 两条渲染路径（`GL_POINTS` / 实例化四边形）与生产的差异**几乎相同** ⇒ ⇒ 与图元拓扑无关。

⇒ ⇒ **差异不在逻辑**，而在**两套 GL 实现对「点图元边缘覆盖」的判定不同**
（生产走浏览器原生 WebGL2；引擎走 wgpu 的 GLES 后端）⇒ ⇒ **实现级差异**。

⇒ ⇒ 因此判据**不能**是「差异必须为 0」（那会恒红且无解），
⇒ ⇒ 也不该是「随便放宽到一个百分比」（那会放过**真正的语义回归**）
⇒ ⇒ 正解是**把差异约束在可解释的形态内**：

> **判据**：差异像素**必须全部落在粒子边缘带内**（离粒子轮廓 ≤ N 像素），
> 且**占比 ≤ 预算** ⇒ ⇒ 实现级边缘差异被**明确豁免且有界**；
> 而语义级回归（位置 / 颜色 / 数量 / 半径错）会**产生带外差异** ⇒ ⇒ **当场红**。

⇒ ⇒ 实现状态见台账 **E-60**（门禁脚本 `crates-ui/evidence/p5-b/check_particle_edge.py`）。

## 4. 后果

### 4.1 正面

- 片头**从此可测**：生产那 1,000+ 行 GLSL 之前是黑盒，现在有 Rust 单测 + 逐值对照装置
  ⇒ ⇒ 立项的**第一个真问题（渲染层不可测）在片头上被解决**；
- GPU 层有**第二阶段（弃 WebView、走原生窗口）**的地基（ADR-0015 §129 的既定方向）；
- 边界**有守卫**，不再靠记忆。

### 4.2 负面（**必须记住**）

- **点图元 / 四边形双路径**是**长期**维护成本（WebGPU 规范**没有点尺寸**
  ⇒ ⇒ 点精灵只能用实例化四边形模拟）⇒ ⇒ 两条路的**边缘覆盖规则**必然不同；
- 因此「引擎与生产**逐像素全等**」在片头上**不作为验收标准**，
  改用 §3 的**有界差异**判据 ⇒ ⇒ 这是**明确的取舍**，不是含糊。

### 4.3 不变

- 引擎**仍不**写 CSS 引擎 / 滤镜层 / 排版 / 主题；
- 引擎**仍不**碰 HTTP / SSE 契约与能力门控；
- **0** 引新外部依赖；主仓 **0** 行改动（除本文与配套文档）。

## 6. 复盘

- **决策依据**：owner 口述「留引擎呗」+ §1.2 的三问判据 + §3 的有界差异判据；
- **做得对的**：把「留不留」变成**可判定的**问题（三问），而不是偏好之争；
- **做错的（已更正）**：曾把「两条腿差异掩码相同 ⇒ 与后端无关」当作证据
  ⇒ ⇒ 实为**同一份代码**跑两条腿 ⇒ ⇒ 已在台账更正（E-55）；
- **教训**：**判据自身的缺陷**（cwd 口径、冻结时机、帧数驱动、环境元数据混入比对）
  比引擎缺陷更隐蔽 ⇒ ⇒ 必须有「按 CI 同形条件本地跑」的装置（`scripts/run-ci-local.py`）。
