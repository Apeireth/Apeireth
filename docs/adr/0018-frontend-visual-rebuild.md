## 1. 背景与问题

### 1.1 owner 定调（2026-10-28 口述，逐字摘录）

> ①「我认为现在的前端整体不行……这是一条大胆的重构一切视觉方案的前端线。」（「作战」是形容词）
>
> ②「范式层留不留？回头我们会研讨，设立新范式。」
>
> ③「基底就是我们的自研引擎就行。」——并认可 Hybrid 路径：「Svelte 做设计原型，引擎做最终实现。这个放到做的时候才能看出哪个决定是对的，留待讨论。」
>
> ④ 范围：「一切视觉」包括 3D 形象/场景/桌宠/图标族/启动动画，但**先做业务界面**。
>
> ⑤ 旧线处置：逐像素迁移线**冻结**，已完成件降为「引擎能力证据（不进产品）」；剩余 5 个设置子面不再迁移。
>
> ⑥ 预算口径：不设人日预算，按「每批独立验收 + AI 施工线墙钟」推进；成本门如实标注。

### 1.3 为什么现在必须决策

1. **旧设计是要被替换的对象，不是基线**：owner 判定「整体不行」后，继续在旧设计上做像素级迁移或堆功能 = 把成本持续投进将被替换的对象；旧线的「与旧画面 0 像素差」目标函数与新目标（换一套视觉方案）**不可同时成立**，必须正式废止，否则执行线会用旧门禁否掉新设计。
2. **前端是 V1「上屏面兑现」的唯一卡点**：后端能力在涨、可见面在旧结构里继续变厚（62 组件 / 5,314 行设置页 / 38 条源码镜像测试）⇒ 视觉债 × 功能债 × 测试债三重放大。
3. **范式未立前不能写代码**：owner 明确「回头研讨，设立新范式」。范式未定时任何「重设计」都是无根漂移 ⇒ 新线第一步必须是「范式研讨会 + 方向打样」，而不是开工。

### 1.4 本 ADR **不**决定的事项

| 不决定 | 由谁 / 何时定 |

| 生产切换的时间点与开关形态 | W4 计划门 |

## 2. 决策

> **一句话**：Apeireth 前端进入「视觉总攻」——以自研 Rust 引擎为**最终目标基底**，推倒重建**全部视觉方案**；先业务界面、后华服；旧设计只作参考，不再作为验收基准。

| # | 子决策 | 改什么 | 不改什么 |
|---|---|---|---|
| **D1** | **目标函数更换** | 验收从「与旧 Svelte 逐像素差 ≤1%」改为「新视觉方案成立（owner 审美门）+ 行为/数据门 + 0 装」 | 旧像素对照装置**保留**为回归/能力工具（可继续用来验证引擎渲染正确性），但**不再是产品目标** |
| **D2** | **基底 = 自研引擎** | `crates-ui` 为最终实现载体（wasm32 → Tauri WebView）；`ui-core` / `ui-dom` / `ui-macro` / `ui-gpu` + 独立 CI + 证据装置保留为地基；`ui-kit` 按新设计**重建** | 独立 workspace 形态、主 workspace 0 依赖、Tauri 宿主不改 |
| **D3** | **Hybrid 打样** | W1 用 Svelte 做**设计原型载体**、引擎做**最终实现载体**同屏对照 | 打样若证引擎达不到设计/工程门，owner 用数据裁定是否调整基底；本 ADR 不预设「引擎必成」 |
| **D4** | **范式另立** | 新范式由 owner 主持研讨会定稿（W0）；以新范式文档为准 | 新范式落地前，`00-PHILOSOPHY.md` / `01-DESIGN-SYSTEM.md` 只作**输入**，不作约束 |
| **D5** | **范围序** | 业务界面（会话 / 工作台 / 工具 / 审批治理 / 设置 / 状态条 / 空错态 / 通知 / 快捷窗 / 诊断）优先 | 华服线（3D/场景/桌宠/图标族/启动动画）排其后，另出计划；**不是砍掉** |
| **D6** | **旧线冻结** | 0015 的「视觉层零改写」与「逐像素迁移」目标废止；在途 80,609 行冻结为「引擎能力证据（FROZEN）」，不进产品；剩余 5 个设置子面不迁 | 已建成引擎代码不删除（作为地基与参考）；历史提交记录不追溯改写 |
| **D7** | **硬边界不变** | — | ① 0 触碰 Tauri 宿主与后端契约（数据面照旧）；② 0 装（无真实来源的动效/数据不上屏）；③ 旧前端一直可跑到 W4 切换验收；④ 每批可回滚；⑤ LOCKED 5 项 0 触碰；⑥ 主 workspace 0 改动 |

**为什么「基底 = 引擎」与「Hybrid」不矛盾**：引擎是**目标载体**（owner ③），Hybrid 是**建造方法**（先用最快载体把设计试出来，再在目标载体上实现并对照）——两者的分歧点只在「引擎能否达到设计/工程门」，这个分歧由 W1 打样数据回答，而不是现在用立场回答。

## 3. O-6 三阶审查（各含拒的 alternatives + 拒理由）

### 3.1 总体最优

在「owner 判定旧前端整体不行 + 引擎已建成 3.5 万行 + 业务界面必须尽快可见」的语境里，这条线的最优切入点是**「设计方向先行 + 引擎打样验证」**，而不是直接开工写界面。

- **拒「继续在 Svelte 上做视觉重构」**：旧结构债（62 组件 / 5,314 行设置页 / 38 条源码镜像测试）会把新设计锁死在旧形状里；且 owner 已定引擎为基底 ⇒ 在 Svelte 上重做视觉等于把工作量付两次。
- **拒「保留旧设计，只换实现/引擎」**：owner 判定旧设计整体不行，这等于把沉没成本当目标；且「与旧画面 0 像素差」与「换一套视觉方案」互相否证。
- **拒「先全量补引擎能力，再开始设计」**：设计方向未定时，能力投入没有靶子；且「补完引擎」是无自然终点的清单（会无限膨胀）。正确顺序是**设计原型反向拉出能力清单**。
- **拒「大爆炸式一次性重写并直接替换生产」**：不可回滚、不可分批验收、owner 审美介入点太少 ⇒ 大概率产出「精致但依然不行」的东西。

### 3.2 系统最优

- **改动放前端层**：后端（`crates/**`）、宿主（`src-tauri/`）、契约都不动 ⇒ 与主仓所有并行线**零文件冲突**；新线只写 `crates-ui/**` + `docs/design/**` + 本线计划文档 + 独立 CI。
- **拒「把 UI 渲染放进主 workspace」**：会破 0 引新外部 dep 与主图 0 变化纪律；独立 workspace 是 0015 已裁决的形态，保留。
- **拒「设计系统继续用 Svelte 组件 + CSS 手写为长期形态」**：旧线的核心教训是设计/实现没有单一真源（CSS 原文复用只是迁移期手段）；新线要求设计令牌与组件规范由**生成器/单一真源**驱动，两侧（原型/引擎）同源。
- **拒「数据面跟着视觉一起重写」**：`runtime.ts` 的 HTTP/SSE 契约与 Tauri commands 是既有资产；新前端按后端契约**重新核对**，但不重写后端。

### 3.3 架构最优

- **引擎仍是独立 workspace（7 crate）**：主图 0 变化；新线在 `crates-ui` 内扩（若增删 crate 则另 ADR + 契约 §[vendored].ui_engine 更新）。
- **单一渲染层**：Svelte 仅作**设计原型载体**（短期），不作长期第二套实现 ⇒ 避免双栈设计漂移。
- **单一设计真源**：新设计系统 v1 的令牌与组件规范是唯一真源；原型与引擎都从它生成/对照。
- **拒「新造第二套渲染层」**（如另起 Web 组件框架）：与 0015 已投入的引擎核心重复，且制造第三套真相。
- **拒「先切换基底再定设计」**：架构服务于设计目标，顺序反了会得到「能跑但审美不成立」的产品。

## 7. 后果（Consequences）

**正面**：
- 目标函数单一：不再有「旧设计像素门」与新设计目标互相打架。
- 设计与引擎解耦：设计先试错（便宜载体），引擎只实现**已定稿**的设计。
- 旧线投入不浪费：引擎核心/GPU/证据装置留作地基；旧线证据冻结入库。

**负面 / 接受的代价**：
- 旧线沉没成本：80,609 行冻结为证据，**不转为产品**。
- 双轨期：Svelte 原型 + 引擎实现并存（限 W1），存在设计漂移风险，需单一设计真源控制。
- owner 需投入审美评审时间（艺术总监角色，不可代签）。
- 范式未定前有方向漂移风险 ⇒ W0 硬门先立范式。

**后续 stage**：
- W0 立即启动（owner 研讨会 + 参考采样 + 方向提案）
- 华服线另出计划（业务界面稳定后）
- `00-PHILOSOPHY.md` / `01-DESIGN-SYSTEM.md` 的最终处置（取代/修订/归档）由新范式文档决定
- V1「上屏面兑现」的账目口径由本线与 V-forward-direction 线复核后更新
