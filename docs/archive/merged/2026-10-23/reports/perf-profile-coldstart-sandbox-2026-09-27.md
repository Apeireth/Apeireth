# 冷启动与沙箱 spawn 剖析报告 (2026-09-27)

两条基准红行 —— 「微内核冷启动」与「OS 物理沙箱 spawn」—— 的优化前分段剖析、根因、
优化实现与前后复测对比。剖析先行: 先用分段计时找出大头, 再动手, 全程行为语义零变化
(既有测试零回归)。所有数字可用附带脚本一键复跑; 未达标处如实标注差距倍数, 不改口径粉饰。

- 机器: AMD Ryzen 9 9955HX / 32 GB / Windows 11 / rustc 1.97.1 (与
  [`benchmark-reproduction.md`](benchmark-reproduction.md) 同机同日)。
- 复跑命令: `pwsh -NoProfile -File scripts/run-benchmarks.ps1 -Bench <key>`;
  剖析子命令 `profile-cold-start` / `profile-sandbox` 由基准 harness 提供
  (诊断用, 不计入 README 目标行)。

---

## 1. 结论速览

| 红行 | 优化前大头 (剖析定位) | 优化 | 优化后 |
| :--- | :--- | :--- | :--- |
| OS 物理沙箱 spawn | **受控创建路径的挂起子进程主线程恢复**: 系统全线程快照+遍历 ≈ 27 ms/次; 其次监督循环 10 ms 轮询步长 ≈ +5 ms; 子进程本身仅 ≈ 8 ms | 创建句柄直接 `ResumeThread` + 事件化等待 | P50 **47.3 → 12.6 ms ✅ 达标** (P99 15.2 ms 略超目标, 如实标注) |
| 微内核冷启动 | **会话存储连接池 build 时急切建满 10 条文件连接** (省下 ≈ 4~11 ms, 随负载) + 两个全新库的文件创建/schema DDL (合计 ≈ 18 ms, 其中文件系统侧 ≈ 8.5 ms/库) | 连接池启动期 1 条空闲连接 + 迁移执行编排合并为单事务提交 | P50 **22.0 ms, 仍 ❌ (差距 2.2×)**, 诚实标注 |

关键反转: 优化前报告曾推测沙箱 spawn 的大头是「子进程冷启动不可消」—— 分解实测推翻了
该推测: 纯子进程地板 (spawn + 等待退出 + 输出读取, 无执行器) 只要 **8.0 ms**, 而
无隔离 execute 全程 43.4 ms、沙箱 execute 全程 49.6 ms —— 大头在**执行器受控创建路径**,
不在子进程。修复后无隔离 execute 全程 7.5 ms ≈ 子进程地板 (执行器附加 ≈ 0.2 ms),
受控边界增量 ≈ 5.1 ms。

## 2. 剖析方法

1. **冷启动分段计时**: 基准 harness 新增 `profile-cold-start` —— 与 `cold-start`
   目标行**同一实现路径**, 只加 4 个计时点 (合计 < 1 µs), 输出四段首尾相接的分段统计;
   另附两个参照: 同库二次打开 (迁移簿记空跑) 与纯内存库打开 (同迁移集、无文件 I/O),
   把「建库 DDL 计算」「文件系统侧成本」拆开。
2. **沙箱 spawn 分解**: 基准 harness 新增 `profile-sandbox` —— 子进程地板 / 无隔离
   execute 全程 / 沙箱 execute 全程 / AppContainer 身份获取 / 目录授权 / 平台能力查询。
3. **进程创建路径探针** (独立计时程序, 不入库): 拆解 std 挂起创建、线程快照、线程遍历、
   `OpenThread`+`ResumeThread`、轮询等待、阻塞等待各占多少。

## 3. 冷启动分段计时 (优化前, n=30, 每轮全新数据目录)

分段剖析首两轮 (同代码, 第 2 轮负载较低; 括号为第 2 轮 P50):

| 分段 | 口径 | P50 (ms) | mean (ms) | 备注 |
| :--- | :--- | ---: | ---: | :--- |
| 记忆存储打开 | `SqliteMemoryStore::open` (建库/开连接 + 记忆 schema 迁移) | 13.33 (13.41) | 13.64 | 含首建 schema DDL |
| 会话存储打开 | `SqliteSessionStore::open` (连接池 + 存储迁移) | 20.85 (13.42) | 18.98 | **最大段** |
| 模块集组装 | `ProductionModules::build` | 0.011 | 0.012 | 纯内存构造, 可忽略 |
| Runtime build | `register_into` + `build().await` 到 ready | 0.038 | 0.046 | 可忽略 |
| **全程合计** | 四段首尾相接 (≈ cold-start 口径) | **33.85 (27.65)** | 32.68 | |

参照拆分 (同口径附测):

| 参照 | P50 (ms) | 读法 |
| :--- | ---: | :--- |
| 记忆存储-内存库打开 | 4.14 | 同迁移集打在纯内存库: 计算成本 ≈ 4.1 ms |
| 记忆存储-同库重开 | 2.10 | 迁移已应用: 开连接+簿记 ≈ 2.1 ms |
| 会话存储-内存库打开 | 0.95 | 池+迁移、无文件 I/O ≈ 1.0 ms |
| 会话存储-同库重开 | 12.86 | **同库重开仍要 ≈ 13 ms** → 池急切建连是独立大头 |

归因 (会话存储): 重开 (无建库 DDL) 与内存库打开 (无文件 I/O) 之差 ≈ 12 ms, 全部落在
`SqliteConnectionPool::build` —— 连接池在 `build()` 时**急切建满 `max_size = 10` 条**
文件连接, 每条 = 一次文件打开 + PRAGMA 初始化 (WAL 转换), 是启动期重复 I/O。
归因 (记忆存储): 计算 (迁移 DDL + 触发器) ≈ 4.1 ms, 首建文件库 ≈ +9.3 ms
(库文件 + WAL/SHM 文件创建与写入的系统侧开销, 逐轮新库语义下无法省略)。

## 4. 沙箱 spawn 分解 (优化前, n=50)

| 分段 | 口径 | P50 | mean | 读法 |
| :--- | :--- | ---: | ---: | :--- |
| 子进程地板 | `cmd.exe exit 0` 纯 spawn + 等待 + 输出读取 (无执行器/无 JobObject/无沙箱) | 8.00 ms | 8.10 ms | 子进程自身启动成本下界 |
| 无隔离 execute 全程 | `ProcessExecutor` 同款执行 (无隔离要求) | 43.37 ms | 43.43 ms | 执行器+受控创建 ≈ 35 ms |
| 沙箱 execute 全程 | `ProcessExecutor` 沙箱执行 (文件/网络隔离 Enforced) | 49.59 ms | 49.71 ms | 受控边界增量 ≈ 6.2 ms |
| AppContainer 身份获取 | `AppContainerSandbox::acquire` (profile 校验 + SID 派生) | 2.72 ms | 2.82 ms | 每次沙箱 execute 都支付 |
| 工作区目录授权 | `grant_directory` (ACL 读-合并-写) | 0.14 ms | 0.15 ms | 每次沙箱 execute 都支付 |
| 平台能力查询 | `current_platform_capabilities` (实测探针, 首跑后缓存) | ~0 µs | ~0 µs | 已缓存, 不是成本 |

结论: 受控边界增量 ≈ 6.2 ms 里 AppContainer 身份获取占 2.7 ms; 而「沙箱 vs 子进程地板」
的 41.6 ms 差距**全部在执行器的受控创建/回收路径** —— 进入 §5 探针拆解。

## 5. 根因探针: 受控创建路径的 ~35 ms 去哪了

独立计时探针 (挂起创建 + 恢复 + 等待, 每项 n=17~45, 均值):

| 探针 | 结果 | 读法 |
| :--- | ---: | :--- |
| 纯 spawn + 阻塞等待 (不挂起) | 总 7.60 ms (创建 1.24 + 等待 6.34) | 子进程地板 ≈ 探针一致 |
| 纯 spawn + 轮询等待 (10 ms 步长) | 总 11.83 ms | 轮询步长 ≈ +4.2 ms |
| 挂起创建 + 线程搜索恢复 + 阻塞等待 | 总 38.05 ms (**创建+恢复 30.64**) | **恢复路径是大头** |
| 手写 `CreateProcessW` (挂起 vs 不挂起) | 创建均 1.14 ms, 无差异 | 挂起创建本身无损 |
| 线程快照 (`CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)`) | 2.0~5.6 ms | 快照不是主犯 |
| 快照后 `Thread32First/Next` 遍历找目标线程 | **24.4 ms (6516 条线程)** | **遍历是主犯** |
| `OpenThread` + `ResumeThread` (直取句柄) | 0.03 ms | 直接恢复几乎免费 |

根因: 挂起创建的子进程恢复时, 被测边界用 `CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)`
枚举**系统全部线程**再逐条 `Thread32Next` 找到目标进程的主线程 —— O(系统线程数),
本机 6516 条线程时 ≈ 27 ms/次 (快照 + 遍历), 每次 execute 都支付; 再叠加监督循环
10 ms 轮询步长的唤醒延迟 (均值 ≈ +5 ms)。而 `CreateProcessW`/`CreateProcessWithTokenW`
**在创建时就返回主线程句柄** (`PROCESS_INFORMATION.hThread`), 直接 `ResumeThread`
即可 (0.03 ms) —— 遍历完全不必要。

## 6. 优化实现 (行为语义零变化)

| # | 改动 | 位置 | 语义保证 |
| :--- | :--- | :--- | :--- |
| 1 | 监督循环事件化等待: `ManagedChild::wait_timeout` (Windows 侧 `WaitForSingleObject` 有界等待, 退出即唤醒; 无事件原语的平台以 1→10 ms 退避轮询兜底) | `process/mod.rs`, `process/windows.rs` | 超时语义不变 (到 `max_runtime` 即杀树); 退出检测只更及时 |
| 2 | 受控创建路径直接 `ResumeThread(pi.hThread)` (创建句柄), 删除沙箱/受限 token 路径的全线程搜索 | `process/windows.rs` | 同一次恢复动作, 只是不再搜句柄; 挂起→入 Job→恢复次序不变 |
| 3 | 无隔离路径同款直接创建 (`CreateProcessW`, std 对齐的命令行引用与可执行解析; batch 脚本与 `\\?\` 逐字路径类**仍走原 std 创建路径**) | `process/windows.rs` | 该类创建/解析语义逐条对齐 (stdin 仍 NUL 设备); 对照口径与沙箱口径对齐 |
| 4 | 连接池启动期只建 1 条空闲读连接, 其余按需补充 (`max_size` 上限与并发语义不变) | `engine/storage/pool.rs` | 查询/写入/并发上限语义不变, 只是建连时机后移 |
| 5 | 记忆库迁移执行编排合并为**单事务提交** (历史迁移 SQL 逐条不动, 幂等不变; BEGIN IMMEDIATE 写锁覆盖读-判-写) | `engine/memory/migrations.rs` | 迁移全有或全无, 幂等重跑不变 |

既有测试零回归: tools 275+ (含真实子进程的 25 项执行器测试: 引号/Unicode 参数、
显式 cwd、环境隔离、输出限额、超时杀树、Job Object、受限 token fail-closed)、
storage 130+、memory 803+ 全绿; `cargo test --workspace --locked` / clippy 0 警告 /
fmt 0 diff 见 §10。

## 8. 双口径讲透 (沙箱 spawn)

- **严格口径 (表判定口径)**: `os-sandbox-spawn` = `ProcessExecutor` 沙箱执行
  `cmd.exe exit 0` 全程 = 边界初始化 + 受控进程创建 + 等待退出 + 输出捕获,
  **含子进程自身启动成本** —— 「起一个受控进程」的真实成本。
- **受控边界增量口径**: 沙箱 execute − 同款无隔离 execute (均值口径),
  优化后 ≈ 5.1 ms (AppContainer 身份获取 2.6 ms + 目录授权 0.1 ms + 属性表/路径
  解析/回收其余 ≈ 2.4 ms)。JobObject 创建+限额单独实测 P50 1.6~2.0 µs。
- 两个口径都列、都不粉饰; 优化让严格口径从 47.3 ms 降到 12.6 ms、增量口径从
  ≈ 4.0 ms 变为 ≈ 5.1 ms —— 增量口径略升的原因: 对照路径与沙箱路径同步去掉各自的
  ~27 ms 线程搜索后, 残差中 AppContainer 身份获取 (未优化, 保自愈语义) 占比凸显。
  **不为好看改口径**: 严格口径 (spawn 全程, 含子进程启动+等待) 仍是表判定口径。

## 9. 诚实边界与剩余空间

- **微内核冷启动仍 ❌**: 优化后 P50 ≈ 22 ms vs 目标 10 ms, 差距 ≈ 2.2×。残余大头 =
  真冷口径 (每轮全新数据目录) 的新库文件创建 + schema DDL: 计算侧 ≈ 4.3 ms
  (内存库参照), 文件系统侧 ≈ 8.5 ms/库 (库文件 + WAL/SHM 文件创建与写入的系统侧开销,
  与本机文件扫描开销强相关)。把这两个成本挪出计时区间 = 改口径, 不做。
- **AppContainer 身份获取 ≈ 2.7 ms/次**: 每次沙箱 execute 都重新校验 profile 并派生
  SID; 进程级缓存可再省 ~2.7 ms, 但会失去「profile 被外部删除时逐次自愈」的现行为 ——
  本轮不动 (语义优先), 留作已知空间。
- **batch 脚本与 `\\?\` 逐字路径类**仍走原 std 创建路径 (含线程搜索 ≈ 27 ms) ——
  不在基准行口径内; 语义逐字保留优先于速度。
- **P99 小样本**: cold-start n=30 / os-sandbox n=50 的 P99 本质是顶部样本; 判定按 P50
  对目标, P99 如实呈现。
- **轮间噪声与并发负载**: 本机当日有间歇性并发负载 (构建/测试), 冷启动这类
  以文件创建为主的口径对它极敏感: 空闲窗口两轮 P50 22.0~22.6 ms (stddev ≈ 1.2),
  并发窗口读数升至 33~48 ms 并出现 478 ms 级停顿尖峰 (见 §7.2)。全部轮次原样呈现、
  不取平均; os-sandbox 各轮一致性好 (P50 12.3~12.8, 共 6 轮)。
