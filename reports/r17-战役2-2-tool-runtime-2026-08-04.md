## 7. 经验教训 (战役 2-2)

1. **VCP regex `i` flag → Rust `(?i)`**: VCP 用 `/(?:...)/i` 大小写不敏感, Rust `Regex::new` 默认 case-sensitive, 容易漏 `(?i)` 前缀。`mask_env_assignment` test 失败才发现 (PASSWORD 大写匹配不到 password pattern)。修复: 正则前面加 `(?i)`。

2. **MutexGuard 非可重入**: `apeireth-memory::SqliteMemoryStore::conn()` 返 `MutexGuard<Connection>`, `std::sync::Mutex` 不可重入。如果在同一个 scope 内先后 `store.conn()` 两次, 第二次会死锁。修复: 用 `{}` scope 显式限制第一次 MutexGuard 生命周期, 或抽到独立函数。

3. **VCP 字段 marker CJK vs ASCII**: VCP 用 `「始」 / 「末」` (CJK), 我们的 ASCII `<<< / >>>` 兼容性更好 (LLM 训练数据里 ASCII 多), 但失去跟 VCP marker 字符串的 1:1 对应。这是 Apeireth 优势 (L1 兼容性), 不是缺陷。

4. **VCP 14 字段平铺 vs Apeireth JSON payload**: VCP `tool_call_records` 表 14 列 (id / tool_name / caller_signature / ...), 我们用 `HistoryEntry.payload: serde_json::Value` 塞全部。优点: 灵活 + 不破坏 6 流 schema, 缺点: 不能 SQL 直接 `WHERE tool_name = ?`。可接受 (战役 2-2 不要求 SQL 查询)。

5. **apeireth-protocol dep 提前 wired**: Cargo.toml 列入 `apeireth-protocol = { path = "../apeireth-protocol" }`, 但战役 2-2 实际未使用 (parser/executor/privacy/record/fuzzy 不依赖 protocol 类型)。可作为未来接 pipeline 时的接入点 (战役 1-1 protocol 已建, 战役 2 完时串接)。
