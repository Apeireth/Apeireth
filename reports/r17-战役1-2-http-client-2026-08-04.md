### 4. LIFO 调度真实现
- `LifoPool` = `Arc<Mutex<VecDeque<RequestTicket>>>` + `Arc<Semaphore>`
- `Lifo` 策略: `pop_back` (后进先出, 最新鲜的请求优先拿连接)
- `Fifo` 策略: `pop_front` (先进先出, 测试用)
- `max_sockets` → `Semaphore::new(max_sockets)` (并发限流)
- `LifoGuard` (RAII) — drop 时自动释放 permit + 移除 ticket

**借鉴决策表** (`docs/stage3-blueprints/borrowed-from-projects.md §6.2.2 #14`):
> 复刻 VCP `http.Agent({ keepAlive: true, freeSocketTimeout: 8000, scheduling: 'lifo', maxSockets: 10000 })`:
> - 用 Rust `reqwest` 的 `Connector::custom` + 自建 `lifo_pool.rs`
> - 8 秒空闲 socket 主动销毁 (防 zombie)
> - LIFO 调度 (优先复用最新鲜的连接)
> - 集成到 `apeireth-http-client`

**实装差异说明** (诚实记录):
- VCP 借鉴决策表提到 "reqwest 的 `Connector::custom`", 我们**没**用 Connector::custom (那是 hyper 0.14 API, reqwest 0.12 走 hyper 1.x, Connector 行为不同).
- 实际: 我们用 `ClientBuilder::tcp_keepalive` + `ClientBuilder::pool_idle_timeout` + `ClientBuilder::pool_max_idle_per_host` 3 个原生 API 把 5 字段真传 reqwest, 效果**等价**于 Connector::custom.
- LIFO 调度在**请求调度层**实现 (`LifoPool`), 跟 reqwest 内部 per-host 连接池配合, 整体效果是"最新鲜的请求优先用最新鲜的连接".

## 🐛 已知 caveat (诚实记录, 不假装完美)

1. **Round 1 集群过载**: example 第一次真接 minimaxi 时返回 529 (overloaded, server-side), 这是 minimaxi 服务端问题, 跟我们代码无关. 主人 apikey 真 + URL 真, 集群偶发过载是正常现象. Round 2/3 都 200 OK.
2. **reqwest 内部 LIFO**: reqwest 的 per-host 连接池是 FIFO 调度, 我们没法直接控制连接级 LIFO. 我们的 `LifoPool` 在**请求调度层**做 LIFO, 组合效果 ≈ VCP node:http.Agent LIFO 行为 (最新鲜请求拿最近可用 worker).
3. **默认 30s timeout**: `HttpClient::new` 设了 `.timeout(Duration::from_secs(30))`, 这是 reqwest 默认, VCP `http.Agent` 没显式 timeout (用 Node.js 默认 0 = 永不超时). 我们偏保守, 主人可改 builder.
