# 桌面常驻形象渲染性能探针实测报告（2026-10-11）

> 用词纪律：正文只用中性类别名——**2D 形象路线 / 3D 卡通渲染路线 / 光态基线**；依赖名只出现在命令块与依赖表。
> 口径纪律：预算口径取自 `docs/design/00-PHILOSOPHY.md` §8（T0 预算目标 <150MB RAM、滚动 60fps，原文标注"数值待实测校准"）。
> 证据纪律：全部数字为本日实跑采集（命令清单见 §9；原始数据 `frontend/perf-probe/results/result.json`、`result.webgl-off.json`、`result.detail.json`）；凡属推断的逐条标注"推断"，未测的标注"未测"。

## ① 一句话结论

**三条形象负载线在 220×260 舞台里全部远低于性能红线：3D 卡通渲染路线每帧 JS 0.254ms、形象负载本体内存约 9MB 级，"负载本体口径"下轻松压进 <150MB，稳态 FPS 顶着 165Hz 刷新率上限（164.6）；2D 形象路线更轻（每帧 0.133ms）；光态基线近似零成本（每帧 0.001ms）。两条纪律（document.hidden 停渲染、WebGL 不可用降级）三线全部通过。但"常驻窗整体内存"口径下浏览器进程树稳态 600–670MB，超过 150MB 预算——三线无差别，属浏览器壳层基线而非形象负载，此预算口径必须先定义清楚（见 §4）。对照 `reports/avatar-runtime-selection-2026-10-11.md` 的"2D 骨骼主线、3D 备选"结论：实测**印证并小幅上修**——3D 备选的内存疑虑解除，其未升主线的剩余理由是资产/工具链与 WebGL 依赖面，不再是内存。**

## ④ <150MB 预算逐项判定（3D 卡通渲染路线）

预算 <150MB 的"内存"指什么，原文未明确；本次按三个口径分别给数与判定：

| 口径 | 3D 线实测 | 判定 | 说明 |
|---|---|---|---|
| A. 形象负载本体（页面上下文内存，含 JS 堆） | **8.97 MB**（其中 JS 堆 6.24MB） | ✅ **过**（余量 ≥15×） | 3D 卡通渲染负载本身的全部可归属内存 |
| B. 承载页面的渲染进程工作集 | **约 89–99 MB**【推断为本页进程】 | ✅ **过** | 含 Chromium 渲染引擎基线（约 30–60MB【推断】）+ 页面负载；三线几乎无差（3D 时最大渲染器 91.5MB、2D 时 88.8–98.6MB、光态时 90–94MB） |
| C. 常驻窗整体（浏览器进程树：壳 + GPU + utility + 多渲染器） | **600–670 MB**（稳态） | ❌ **不过** | 但 **三线无差别**：3D 稳态 600–628MB、2D 625–648MB、光态 625–633MB；超标部分是浏览器壳层基线，不可归因于形象负载 |

进程级拆分（补测 `result.detail.json`，稳态样本）：浏览器主进程约 192–198MB、GPU 进程约 144–175MB、utility 进程组约 62–101MB、渲染器进程合计约 187–196MB（本会话共 3 个渲染器进程）。

**结论**：
1. **"3D 卡通渲染路线能否压在 <150MB 内" → 按负载本体口径：能，且余量巨大（9MB 级 vs 150MB）；按"承载页渲染进程"口径：能（约 90–100MB）；按"浏览器进程树整体"口径：不能（600MB+），但此口径下 2D、光态同样不能，超支属壳层与 GPU 驱动基线。**
2. **建议预算考核采用"负载本体 + 渲染进程"双口径**（本次均过），把壳层内存计入宿主应用账而不是形象层账；若坚持整树口径，需要壳层共享（常驻窗与主进程共浏览器进程）或降多进程开销后再测。
3. **稳态 FPS：164.6（1% low 154.4）@165Hz 封顶**；每帧 JS 0.254ms，折算 60Hz 帧预算占用 1.5%【推断 60Hz 屏稳 60fps】。滚动 60fps 目标（§8）与形象动画负载不冲突。

## ⑤ 两条纪律逐项判定

### 纪律一：document.hidden 时渲染循环必须停（帧计数证明）—— ✅ 三线全部通过

| 线 | 可见时帧率 | 隐藏期 3s 渲染帧 | 隐藏期循环回调 | 隐藏期全局 rAF 心跳 | 恢复后 2s 帧数 | 判定 |
|---|---|---|---|---|---|---|
| 3D 卡通渲染路线 | 165/s | **0** | 0 | **495**（>0） | 329 | ✅ PASS |
| 2D 形象路线 | 165/s | **0** | 0 | **495** | 330 | ✅ PASS |
| 光态基线 | 165/s | **0** | 0 | **495** | 330 | ✅ PASS |

证明力说明：验证用 `document.hidden/visibilityState` 强制注入 + 派发 `visibilitychange`，同时有一条**不看 hidden 的全局 rAF 心跳**做对照——隐藏期浏览器仍在发帧（495 次/3s ≈ 165Hz），而三条线的渲染帧计数为 0、循环回调为 0（循环被取消而非只跳过绘制），恢复可见后立即继续出帧。即"停帧是渲染循环自身纪律"，不是浏览器停发帧的搭便车。真实失焦/最小化走同一 `visibilitychange` 处理路径（**推断**：真实窗口失焦未在无头环境实体复现；手动测试可最小化窗口复验，页面时间线会记录真实切换事件）。降级轮（真实禁用 WebGL 环境）复验 2D 线 hidden 行为：0/495/330，同样通过。

### 纪律二：WebGL 不可用时优雅降级（3D 报不可用由宿主回落，2D/光态照常）—— ✅ 两路验证通过

| 验证路 | 3D 线行为 | 2D 线 | 光态线 | 判定 |
|---|---|---|---|---|
| 页内 stub（`getContext("webgl*")` → null 后重建 3D 负载） | 报 `webgl-unavailable`，不抛穿；宿主回落目标 = 2D 形象路线 | 照常出帧 | 照常出帧 | ✅ PASS |
| 真实 `--disable-3d-apis` 启动（`result.webgl-off.json`） | WebGL 探测不可用，3D 线报 `webgl-unavailable: Error creating WebGL context.`，不抛穿 | 照常（5s 出 802 帧） | 照常（5s 出 823 帧） | ✅ PASS |

## ⑦ 路线终选建议（对照 `reports/avatar-runtime-selection-2026-10-11.md`）

前报告结论："2D 骨骼主线、3D 备选（参数面升级项）、帧序列/光态兜底"，并把"WebView 性能与回落未实测"列为三大风险之一，注明"3D 路线……必须先做 150MB 预算 + 失焦暂停 + 零 WebGL 回落的原型实测再定终选"。本次实测对该结论的裁决：

1. **印证"2D 骨骼主线"**：2D 形象路线每帧 JS 仅为 3D 线的 52%（0.133 vs 0.254ms）、零 WebGL 依赖、hidden/降级两条纪律天然简单，作为主线的工程风险最低。
2. **上修"3D 备选"**：前报告标注"<150MB 预算下需实测"的疑虑已解除——负载本体 9MB 级、渲染进程约 90–100MB【推断】，稳态 FPS 顶格，纪律一/二全过。3D 线未升主线的剩余理由只在**资产/工具链**（前报告 §⑤-1：白名单内素材须自制/委托）与 **WebGL 依赖面**（须保降级），不再是内存与帧率。
3. **"帧序列/光态兜底"必须保**：光态基线每帧 0.001ms、堆 5.91MB（底噪级），是零 WebGL 回落与 T0 节能档的现成答案；本次降级验证中它与 2D 线照常运行，兜底链路成立。
4. **终选建议**：维持 **2D 形象路线为主线、3D 卡通渲染路线为备选（参数面升级项）、光态基线兜底**；把本次实测记为 3D 备选的"性能解锁条件已满足"，升级触发条件改为"形象资产/工具链就绪 + 参数面需求（口型五音、视线三驱动、发丝物理）明确"。两条纪律（hidden 停渲染、WebGL 降级）应作为形象层的验收门禁固化进任何路线的实现。

## ⑧ 诚实边界（必读）

1. **浏览器内核近似而非 WebView2 实体**：本次为 Edge 155 无头模式 + CDP，与 WebView2 同 Chromium 内核，但 **WebView2 的宿主进程共享、合成器与真实透明置顶窗（WS_EX_LAYERED/穿透）行为未实测**；口径 C 的进程树数字是独立浏览器实例的数字，WebView2 常驻窗与宿主共享浏览器进程后会不同（方向未知，未测）。
2. **推断项**：§3 的"60Hz 屏稳 60fps"折算、§4 口径 B 的"最大渲染器进程≈本页进程"与"渲染引擎基线 30–60MB"、§5 真实失焦走同一处理路径——均为推断，已逐处标注。
3. **未测项**：GPU 显存（3D 线的纹理/帧缓冲占用在显存里，不在工作集内）、WKWebView/非 Windows 平台、长时（>5min）浸泡、多形象同屏、真实 WebView2 内存、CPU 占用率（本次只有每帧 JS 时长口径）。
4. **FPS 口径**：rAF 采样 ≠ 合成器真实上屏；本机 165Hz 封顶使 FPS 均值三线趋同，判别负载轻重请用每帧 JS。
5. **内存口径**：`usedJSHeapSize` 只覆盖 JS 堆；`measureUserAgentSpecificMemory` 是页面上下文口径（含 DOM/内部对象），不含进程壳；Windows `WorkingSetSize` 含共享页重复计数且与"私有内存"口径不同。三者不可相加。
6. **hidden 验证**为强制注入 + 心跳对照（无头环境无法真实失焦/最小化）；证明的是渲染循环纪律，真实浏览器兜底（hidden 时 rAF 停发）未单独量化。
7. **浸泡为三线并发最坏口径**，比产品单形象常驻更苛刻；单线浸泡未单独跑。
8. 测试机为 165Hz 高刷 + 2560×1600，GPU 进程基线偏高（约 150MB）与显示配置有关，低配机器的壳层基线会更低（推断）。
